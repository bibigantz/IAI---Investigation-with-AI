Deep Link Drill — Custom URI schemes can send your SMS

A "deep link" is just a URL the app's manifest claims it can handle. When the user taps a link with that scheme, Android resolves the matching app and hands it the URL — including any data sitting in the path or query. This drill shows how a malicious app can use an innocent-looking deep link to fire off SMS messages on the user's behalf.

What you'll learn

  • How intent-filters in the manifest declare which URLs an app responds to.
  • Why custom schemes (smssender://) aren't owned by anyone — multiple apps can claim them.
  • How an app holding SEND_SMS can be wired to send a message just because the user clicked an HTML link.
  • How to reproduce the same behaviour from adb shell am start without any HTML at all.

1. Background — what is a deep link?

An ordinary HTTP URL points to a web page. A deep link uses a URI scheme that one or more native apps register for — instead of opening a browser, Android dispatches the URL to the app whose intent-filter matches. The receiving Activity gets the URL via getIntent().getData() and parses out the bits it cares about (numbers in the path, fields in the query, etc.).

The trust model: Android assumes that opening a URL is a safe operation. The browser and the OS shell follow that assumption; they tap-to-open without confirming. So if the app on the receiving end of the deep link does something dangerous with the URL contents — like sending SMS — the dangerous thing happens silently the moment the user taps the link.

2. The DeepLinkApp's manifest contract

The app you're about to install declares an intent filter for the custom scheme smssender://. The URL format the slide shows is:

smssender://send?data=<phone-number>:<url-encoded-message>

When the app receives such a URL, it parses out the number and message and calls SmsManager.sendTextMessage(...). The app holds SEND_SMS; the OS does not prompt because the permission was granted at install time via -g.

Install gotcha. Samsung Knox / Play Protect blocks the install of any APK requesting SEND_SMS from a non-Play-Store source. You'll see INSTALL_FAILED_VERIFICATION_FAILURE: Install not allowed. Two workarounds:
  1. Settings UI route: push the APK to the phone with adb push deep_link_app.apk /sdcard/Download/, open the file from the Files app on the phone, and accept the "install unknown app" prompt. The user dialog satisfies Knox.
  2. Disable Google Play Protect temporarily: open Play Store → profile icon → Play Protect → ⚙ → toggle "Scan apps with Play Protect" off. Re-enable after the drill.

Exercise — Trigger the SMS via deep link, two ways (slides 41–42)

  1. Install the app: adb install -r -g deep_link_app.apk (apply the gotcha workaround if Knox blocks you).
  2. Method A — through HTML: copy the bundled test.html to the phone with adb push test.html /sdcard/Download/, open the Files app on the phone, tap the file. Fill in a phone number and message, tap the link.
  3. Method B — through ADB directly. Trigger the same deep link without any HTML at all using am start -a android.intent.action.VIEW -d "<deep-link-uri>". The slide gives an example URL — read it, then construct your own.
  4. Open Burp / Logcat / Files-on-phone and confirm the app received the URL and dispatched the SMS.
Hint 1 — The URL shape

The slide example: smssender://send?data=0506944922:hello. Anatomy:

  • smssender — the custom scheme the app's manifest declared
  • send — the host portion (the app's intent filter probably matches host="send")
  • data=<number>:<message> — query parameter the app parses
Hint 2 — URL-encoding spaces

Spaces in URLs become %20. So "Hello World" → Hello%20World. The slide example uses Hello%20%26%20Welcome for "Hello & Welcome" — note that & in a URL means "next query param", so it must be encoded as %26.

Hint 3 — adb command shape

The action is android.intent.action.VIEW; the data URI is the deep link itself. Quotes around the URI are important because ? and & would otherwise confuse the shell.

adb shell am start -a android.intent.action.VIEW -d "<your-uri-here>"
Hint 4 — How to know the deep link arrived

Open adb logcat | grep -i deeplink in another terminal before you trigger the link. The app prints to logcat when it receives the URI.

3. Why this is a real attack pattern

This drill is the simplest case (the user explicitly fills in a number and taps "Send"). But the same machinery enables more interesting attacks:

  • An attacker controls a third-party website. They embed a hidden link to smssender://send?data=<premium-rate-number>:hi. The user visits the page in their browser, the browser sees a non-http scheme, and asks the OS to dispatch — the SMS app fires.
  • An attacker delivers a malicious app via a different channel (sideload, side-effect of another app). The app declares the same scheme. Now there are two apps claiming smssender:// — the one that wins is the one with the higher intent-filter priority. Read the android:priority attribute trick in Android Vulnerabilities slide 10 notes.
  • An attacker uses a deep link that any preinstalled app may handle (e.g. the dialer's tel: scheme) to perform actions in chained scenarios.

Reflection

  1. The app declares smssender as a custom scheme. Why does Android allow apps to claim arbitrary schemes? What would change if all schemes had to be Google-issued like Play Store package names?
  2. The lab APK was granted SMS permission via -g. On a real install, the user must grant it interactively. Does that prompt mitigate this attack class? Why or why not?
  3. How would you defend an app like this if you had to ship it for legitimate reasons (e.g. an enterprise SMS sender)?
