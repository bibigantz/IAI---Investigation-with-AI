ADB Drill — Driving the phone from your laptop

Two exercises drawn from the Android Debug Bridge slides. First, you learn to launch any app component using adb shell am with intent actions and data URIs. Then you watch RAM grow and shrink as a foreground service runs, gets killed, and is restarted.

What you'll learn

  • How to start activities, services, and broadcast receivers from the command line — without ever touching the phone screen.
  • The difference between explicit intents (-n <package>/.<Activity>) and implicit intents (-a <ACTION> with optional -d <DATA>).
  • How extras (--es, --ez) carry typed key/value pairs into the intent the app receives.
  • How to observe an app's RAM footprint live with dumpsys meminfo and what changes when a foreground service is involved.

1. Background — what is the Activity Manager?

Inside Android, every running window is an Activity. Every always-on background task is a Service. Every "an event happened" delivery is a Broadcast. All three are managed by one system service — the Activity Manager (am). Through ADB you can tell am to start, stop, broadcast, and inspect everything it manages, with all the privileges that the shell user holds.

The am commands you'll use today follow one of two shapes:

Explicit intent — name the component

adb shell am start -n <package>/<.Component>
adb shell am startservice -n <package>/<.Service>
adb shell am start-foreground-service -n <package>/<.Service>

You name the exact app and exact class. Used when you know which app you want to talk to.

Implicit intent — describe what you want

adb shell am start -a <ACTION> [-d <DATA_URI>] [--es key value] [--ez key true|false]

You describe the operation; Android picks an app whose manifest declares matching intent filters. Used when you want to trigger a feature regardless of which app handles it (camera, dialer, browser, sms composer).

Common URI prefixes for -d: tel:, http:, https:, geo:, mailto:, sms:, smsto:.

Setup before you start. Install the AdbTraining app: 
adb install -r -g app-debug.apk
The -g grants every runtime permission upfront so you don't have to deal with permission dialogs during the drill (notably the POST_NOTIFICATIONS one needed by the foreground service on Android 13+).

Instructor demo before Exercise 1 — am start basics (slide 12)

Walked through live on the projector; recorded here in case you missed it on the day.

The simplest case for each of the two intent shapes (explicit and implicit):

# Explicit — name the component
adb shell am start -n il.co.syntax.adbtraining/.MainActivity

# Implicit — describe what to do; the OS picks the app
adb shell am start -a android.intent.action.DIAL -d tel:8768678
adb shell am start -a android.intent.action.VIEW -d http://cnn.com

Try replacing DIAL with CALL in the second line. DIAL opens the dialer pre-filled and waits for a tap; CALL dials directly — but only succeeds if the calling UID holds the CALL_PHONE permission. Shell does (see Day 1's Service Call drill), so on the lab phone CALL would actually attempt to dial. The VIEW example with http://cnn.com opens the default browser at CNN.

Exercise 1 — Open apps with am start (slides 14–15)

Goal: drive the phone entirely through ADB, never touching the screen. Your reference is the Android Common Intents page — it lists, by use case (Alarm clock, Camera, Contacts, Email, Maps, SMS, Web, …), every standard action the platform recognises and the extras each one takes.

  1. Open the AdbTraining app's SecondActivity (the second screen) using an explicit intent.
  2. Open the camera in still image mode using an implicit intent. Then close it and try video mode.
  3. Open the map app to coordinates 32.0833, 34.8167 (use the right URI scheme).
  4. Open the SMS composer to a specific number with the message body pre-filled to Hello World! (one space between the words). Use the right action and the right extra key.
  5. Now do the same SMS, but without using --es. Type the body into the open compose window directly using adb shell input text.
Hint 1 — Activity component naming

The package and class go in the form <package>/.<ClassName>. The leading dot means "relative to the package". For AdbTraining the package is il.co.syntax.adbtraining.

Hint 2 — Where to find the action you need on the Common Intents page

The Common Intents page is organised by use case. Scroll the left-side TOC to find the category — "Camera" for tasks 2, "Maps" for task 3, "Text messaging" for task 4 — then read the section. Each section shows code samples that look like this:

val intent = Intent(MediaStore.ACTION_IMAGE_CAPTURE)

That's a Kotlin constant name, not the action string. You can't pass ACTION_IMAGE_CAPTURE to am start -a. You need the actual string the constant resolves to — see Hint 3.

Hint 3 — Find the actual constant value, not the nice symbol name

This is the single most common student mistake on this exercise. When the docs say:

MediaStore.ACTION_IMAGE_CAPTURE

that is a variable name. It's a label Java/Kotlin code uses. The shell knows nothing about it. The shell needs the string value the constant holds. To find it:

  1. Click the symbol name in the Common Intents page — it links you to the reference page for that class.
  2. On the reference page, find the constant in the alphabetical list of fields. You'll see a block like: 
    public static final String ACTION_IMAGE_CAPTURE

Constant Value: "android.media.action.IMAGE_CAPTURE"
  3. Use the line that starts with "Constant Value" — everything inside the quotes — as the argument to -a.
:: correct — uses the string value
adb shell am start -a android.media.action.IMAGE_CAPTURE

:: wrong — uses the symbol name; nothing matches
adb shell am start -a ACTION_IMAGE_CAPTURE

The same rule applies to extras. If the docs say:

intent.putExtra(Intent.EXTRA_TEXT, "Hello World!")

that's a Kotlin variable named EXTRA_TEXT on the Intent class. The actual key the receiving app reads is whatever string that constant holds. Click through to the reference page:

public static final String EXTRA_TEXT

Constant Value: "android.intent.extra.TEXT"

So on the command line:

:: correct — uses the actual key string
adb shell am start -a android.intent.action.SENDTO -d "sms:0501234567" --es sms_body "Hello\ World!"

:: wrong — uses the symbol name; the receiver looks for "sms_body" and finds nothing
adb shell am start -a SENDTO --es EXTRA_TEXT "Hello\ World!"

(SMS composer is a special case — it doesn't use EXTRA_TEXT; the actual key for its body extra is "sms_body", which you'd discover by reading the Telephony reference. The point stands: look at the value, not the variable name.)

Hint 4 — Spaces in shell strings

The shell tokenises arguments on whitespace. To put a literal space inside an argument that arrives as one extra value, escape the space with a backslash: "Hello\ World!". Same trick applies to adb shell input text.

Hint 5 — Map URIs

Maps use the geo: URI scheme. The format is geo:<lat>,<lng>. No quotes needed if there are no spaces. The Common Intents "Maps" section spells out variations like search-query URIs (geo:0,0?q=...) you can try in the bonus.

Bonus mission — pick two more actions yourself (slide 14)

The slide ends with: "Pick two actions from the page, look at the extras, and try them for yourself." That's the real exercise — using the Common Intents page to discover and run new ones on your own. For each action you pick, write down:

  1. The category (e.g. Alarm clock)
  2. The constant value of the action — the actual android.<…>.action.<…> string you'll pass to -a
  3. The constant value of each extra you need — the actual key string you'll pass to --es / --ei / --ez
  4. The data URI, if any, you'll pass to -d

Three good candidates if you're stuck: WEB_SEARCH (one string extra, easy), SET_ALARM (two int extras for hour/minute + an optional message — practises --ei), and SET_TIMER (one int extra for length in seconds). All three are documented on the Common Intents page.

Don't open the solution yet — read the Common Intents entries for each action, derive the constant value strings yourself, build the command, run it on the phone.

Instructor demo — broadcasting to your own receiver (slide 17)

Walked through live on the projector; recorded here in case you missed it on the day.

The AdbTraining app's MainActivity registers a BroadcastReceiver for the custom action il.co.sytax.MESSAGE_RECEIVER. Send the broadcast and a Toast pops up with the string from the message extra:

adb shell am broadcast -a il.co.sytax.MESSAGE_RECEIVER --es message hello

Now run through the lifecycle, paying attention to when the Toast appears and when it doesn't:

  1. Foreground: launch the activity, broadcast — Toast appears.
  2. Background: press Home (or Back on Android 12-), broadcast again — Toast still appears, because the activity is still alive in the background.
  3. Killed: swipe up from Recents (Android 13+) or adb shell am force-stop il.co.syntax.adbtraining, broadcast again — nothing happens.

Why step 3 fails: the receiver is registered dynamically (in code, in onCreate) — when the activity dies, the receiver dies with it. Static manifest-registered receivers can wake an app from a fully killed state, but since Android 8 (API 26) only a small whitelist of system broadcasts (BOOT_COMPLETED, BLUETOOTH state, etc.) qualify. Custom actions don't. This is the difference between dynamic and static broadcast registration that comes back in the Day 3 Hidden Recognition capstone.

Note: the action string in the slide has a typo (il.co.sytax, not il.co.syntax) — that's the actual string the AdbTraining app registers, so use it verbatim. Don't "correct" the typo or the broadcast won't match.

Instructor demo before Exercise 2 — starting a service (slide 19)

Walked through live on the projector; recorded here in case you missed it on the day.

The MusicPlayerService streams an audio URL from the link extra and plays it through the OS Media Player:

adb shell am startservice -n il.co.syntax.adbtraining/.MusicPlayerService \
  --es link https://syntax.org.il/xtra/bob.m4a

Bob plays. The service then promotes itself to foreground by displaying a notification — required on Android 8+ to keep running when the user navigates away. On Android 13+, the user must also have granted POST_NOTIFICATIONS for that notification to appear; if the app was installed without -g, grant it explicitly:

adb shell pm grant il.co.syntax.adbtraining android.permission.POST_NOTIFICATIONS

Force-stop the app and try again with --ez notif false — the service refuses to show its notification:

adb shell am force-stop il.co.syntax.adbtraining
adb shell am startservice -n il.co.syntax.adbtraining/.MusicPlayerService \
  --es link https://syntax.org.il/xtra/bob.m4a --ez notif false

Within 5–10 seconds the OS terminates the service with ForegroundServiceDidNotStartInTimeException in logcat. The contract is "promote to foreground within 5 seconds, or you die".

Background-vs-foreground start: if the app is already idle (no live activity), am startservice fails with BackgroundServiceStartNotAllowedException — Android 8+ background restrictions. Switch to am start-foreground-service instead. That's exactly the rule Exercise 2 below depends on.

Exercise 2 — RAM usage with a foreground service (slides 21–22)

Goal: watch the AdbTraining app's MusicPlayerService consume memory across its lifecycle. The service streams a music file from a URL and shows a notification while playing.

  1. Start the music player as a foreground service with the URL https://syntax.org.il/xtra/bob.m4a in an extra named link. (You must use start-foreground-service here, not startservice — the slide explains why.)
  2. Read the service's RAM footprint with dumpsys meminfo, filtering for the package name.
  3. Force-stop the app and check meminfo again. What changed?
  4. Start only the MainActivity (no music) and check meminfo a third time.
  5. Now start the activity AND the service. Compare. Then close the activity by swiping up — does the service survive?
Hint 1 — start-foreground-service vs startservice

An app with no foreground component can't start a regular service from the background — Android 8+ rule. start-foreground-service bypasses that rule by promising the service will become foreground (i.e. show a persistent notification) within ~5 seconds. If you forget the -foreground- middle segment, you'll get a BackgroundServiceStartNotAllowed exception in logcat.

Hint 2 — Filtering meminfo for one package

dumpsys meminfo dumps every process; pipe through grep:

adb shell dumpsys meminfo | grep syntax

Or pass the package name to dumpsys meminfo directly for a detailed breakdown of one process:

adb shell dumpsys meminfo il.co.syntax.adbtraining
Hint 3 — Listing processes by package 
adb shell ps -A | grep syntax

The number in the second column is the PID — you can use it instead of the package name in dumpsys meminfo <PID>.

Hint 4 — Force-stop syntax 
adb shell am force-stop <package>

This kills every process and component the app owns, including its foreground service.

Hint 5 — Why the activity-only run uses less memory

An activity in the foreground occupies its own process; a service that the same app owns runs in the same process (unless explicitly declared otherwise). When you start the service, the process pulls in extra libraries (the media player, the notification machinery, the network stack). Activity-only is leaner because none of that is loaded.

Exercise 3 — Spotting an "abnormal" app from its resource fingerprint (slides 24–28)

Two apps come paired: normal_app.apk and abnormal_app.apk. They look identical from the outside — same UI, same package name pattern. Underneath, the abnormal one runs a continuous high-load CPU loop. From a defender's standpoint, the question is: can I tell them apart from adb alone, without seeing the source?

  1. Install both: adb install -g abnormal_app.apk and adb install -g normal_app.apk (the -g just skips runtime prompts).
  2. Start the abnormal app's main activity. Take a baseline dumpsys meminfo reading before tapping the button.
  3. Tap "start heavy CPU operations" on screen, wait ~20 seconds for allocations to accumulate.
  4. Read dumpsys meminfo again. Compare four rows in particular: Java Heap, Dalvik Heap, Native Heap, and TOTAL PSS.
  5. Read its CPU usage with top -n 1 -b. Filter for the package.
  6. Compare every metric against the same readings for com.example.normalapp.
Hint 1 — which tools you'll need

Three commands cover all the steps: am start (you've used this since Exercise 1), dumpsys meminfo <pkg> (you've used this in Exercise 2), and top -n 1 -b (new — single-batch dump of all processes' CPU/MEM). Pipe top through head or grep so you don't drown in 600 rows.

Slide threshold to call something "abnormal": ~100 MB heap growth or 20–30%+ CPU sustained. On the lab phone the abnormal app comfortably exceeds both.

Hint 2 — which heap row should grow, and which should not

This app's Heavy-CPU loop is written in Kotlin and allocates lots of Java/Kotlin objects in a tight loop. Those objects land in the Dalvik Heap / Java Heap rows — those are where you'll see the dramatic growth (typically from ~3–11 MB to well over 100 MB in 20 seconds). The Native Heap row, by contrast, barely moves — it would only grow if the app's heavy work went through JNI / C++ via malloc, which this one doesn't.

So the "what to look for" rule is per-language: Kotlin/Java allocators → Dalvik & Java Heap rows; C/C++ via JNI → Native Heap row. The TOTAL PSS row sums both — it's the one-number summary, but watching the individual rows tells you where the work is happening.

Hint 3 — Why top can show >100% CPU

On a multi-core phone top sums per-core utilisation, so a process pinning all 8 cores would read up to 800%. The A51 has 8 cores. On this app the heavy loop typically reads several hundred per cent — pegging multiple cores. The slide quotes "20–30%" as a rough threshold; we're an order of magnitude above that.

Hint 4 — What this teaches about malware detection

This is the simplest defender's primitive: compare what the app says it does to what its resource use suggests it actually does. A "lightweight questionnaire" that pegs cores and balloons its Dalvik heap to hundreds of MB isn't lightweight. The Day 3 Hidden Recognition capstone is the same idea on a richer canvas — composing many legitimate APIs into a non-legitimate behaviour, visible in resource graphs.

Exercise 4 — Package manager (slide 31)

The pm tool inside adb shell is how you list, locate, install, uninstall, and grant/revoke for any package on the device. Two short sub-exercises:

4A — Find, uninstall, and reinstall the AdbTraining app

Confirm the AdbTraining package is installed. Find where its APK lives on disk. Force-stop the app, uninstall it, then reinstall from app-debug.apk in the course folder. Verify the package is back. The whole sequence is five short adb commands.

4B — Pick any app on the phone (e.g. WhatsApp), pull its APK, dump its manifest

Find WhatsApp's APK path on the device, copy base.apk back to your laptop, then dump its AndroidManifest.xml in human-readable form. The first command produces several paths (one per split APK) — only base.apk matters for manifest analysis.

Hint 1 — useful pm flags from the slide
  • pm list packages -f → also print the on-device APK path next to each package name (saves you a follow-up pm path).
  • pm list packages -3 → user-installed only (filters out system apps).
  • pm uninstall -k <pkg> → keep app data after uninstall (useful for "reinstall preserves my settings" testing).
  • pm grant <pkg> <PERMISSION> / pm revoke … → only works for permissions the app declared in its manifest.
  • pm reset-permissions → no package argument; clears every app's runtime permission grants.
Hint 2 — Why this matters for security analysis

Every step of the "is this app malicious?" workflow goes through these commands: list installed packages → find the suspect → pull its APK → decompile (Day 4 with JADX) and read its manifest. pm path is the bridge between "I see a suspicious package name in pm list packages" and "I have an APK file I can analyse offline".

Exercise 5 — Screen capture: still and video (slide 34)

Two on-device commands cover this; reference syntax from the slide:

  • screencap <path> — single PNG. Use .png extension; .jpg doesn't work (the slide warns about this explicitly).
  • screenrecord [options] <path> — MP4 video. Default max length 3 minutes; --time-limit <sec> to cap shorter; --size WxH to downscale; --verbose to print stats while recording. Press Ctrl+C in the adb terminal to stop early.

Your task: take one screenshot and one short (~5 s) screen recording, then copy both files from the phone to your workstation. Use .png and .mp4 extensions respectively. Save to /sdcard/ on the device. Pull to your laptop with adb pull.

Hint — caveats on Android 13
  • Internal audio recording requires Android 10+ via --audio-source internal; older versions silent-only. The lab A51 (Android 13) supports it.
  • Screen rotation while screenrecord is running is blocked.
  • The output path must be on writable storage — /sdcard/... is the safe choice.

Exercise 6 — Capstone: take a photo from adb alone (slide 38)

Combine the techniques from the earlier exercises. Drive the phone with no screen taps:

  1. Open the camera in still-image mode using an implicit intent. (Same shape as Exercise 1's STILL_IMAGE_CAMERA task — that one launched the app; here you'll keep going.)
  2. Press the shutter button by sending a key event. The slide hints: keyevent 27, or KEYCODE_CAMERA.
  3. Find the file you just took. Photos land in /sdcard/DCIM/Camera/; the new one is the most-recently-modified entry there. Use ls with a sort flag and head/tail.
  4. Pull it with the standard adb file copy.
Hint 1 — What if the shutter doesn't fire on the first key press?

Both forms work: adb shell input keyevent KEYCODE_CAMERA and adb shell input keyevent 27. The Samsung camera app may need a second keycode press if the first is interpreted as autofocus rather than shutter — try pressing twice with a short delay if the first photo doesn't materialise.

Hint 2 — How do I find the file I just took?

The slide uses tail -1, which returns the last line of an alphabetically-sorted listing. That works because Samsung's camera names files YYYYMMDD_HHMMSS.jpg, so alphabetical order = chronological order. ls -t | head -1 is more explicit (sort by mtime, take newest). Both reach the same file when the camera app is the only writer.

Hint 3 — Why this is the capstone

Every primitive in this drill comes back here: implicit intent (Exercise 1), key events (Exercise 1, sub-task 5), file system access via /sdcard (Exercise 5), adb pull (Exercise 5). If you can complete this without consulting the cheat sheet, you've internalised the four-day mental model of "phone is a remote service, adb is the client".

Reflection

  1. Why does an implicit intent (am start -a ...) have to be told a data URI when the action implies a target? What would happen if Android only used the action string?
  2. --es takes a string, --ez takes a boolean. There's also --ei (int) and --el (long). Why does the framework demand typed extras instead of just letting you pass strings everywhere?
  3. You started a service that played music from the internet. The same command lets any shell user point that service at any URL. From a security perspective: is this an issue with the am start-foreground-service command, with the service's design, or with both? Defend your answer.
