Location Drill — Solutions

All commands taken from slides 46–48 of Android Application.pptx. Outputs captured live on the lab Galaxy A51.

Solution — basic assignment (slide 46)

adb install app-location.apk
aapt2 dump xmltree app-location.apk --file AndroidManifest.xml
adb shell am start -n il.co.syntax.location/.MainActivity
adb shell pm grant il.co.syntax.location android.permission.ACCESS_FINE_LOCATION
adb shell pm grant il.co.syntax.location android.permission.POST_NOTIFICATIONS    # Android 13+
adb shell am startservice -n il.co.syntax.location/.LocationUpdatesService
adb shell am force-stop il.co.syntax.location
adb shell pm uninstall il.co.syntax.location

What the manifest tree tells you

Running aapt2 dump xmltree app-location.apk --file AndroidManifest.xml on the lab APK produces (filtered to the interesting lines):

uses-permission android:name="android.permission.FOREGROUND_SERVICE"
uses-permission android:name="android.permission.FOREGROUND_SERVICE_LOCATION"
uses-permission android:name="android.permission.ACCESS_FINE_LOCATION"
uses-permission android:name="android.permission.ACCESS_COARSE_LOCATION"
uses-permission android:name="android.permission.POST_NOTIFICATIONS"
activity android:name="il.co.syntax.location.MainActivity"
    intent-filter:
      action android:name="android.intent.action.MAIN"
      category android:name="android.intent.category.LAUNCHER"
service android:name="il.co.syntax.location.LocationUpdatesService"
    intent-filter:
      action android:name="il.co.syntax.location_tracker_action"

That last action — il.co.syntax.location_tracker_action — is the implicit-intent name you need for the second part.

Solution — activating without permission (slide 47)

# pre-test: install fresh, no -g
adb install app-location.apk
adb shell am start -n il.co.syntax.location/.MainActivity
adb shell am startservice -n il.co.syntax.location/.LocationUpdatesService
# Result: service starts but Fused Location refuses → SecurityException in logcat

# fix:
adb shell pm grant il.co.syntax.location android.permission.ACCESS_FINE_LOCATION
adb shell am startservice -n il.co.syntax.location/.LocationUpdatesService
adb shell am force-stop il.co.syntax.location

The lesson: starting the service is permitted, but the Fused Location call inside the service throws because the calling UID has no ACCESS_FINE_LOCATION. Watch logcat while you trigger this — the SecurityException stack trace points at the FusedLocationProviderClient.requestLocationUpdates call.

Solution — restart from idle with the action (slide 48)

adb shell pm grant il.co.syntax.location android.permission.POST_NOTIFICATIONS    # Android 13+

# start by ACTION (no -n), and use start-foreground-service:
adb shell am start-foreground-service -a il.co.syntax.location_tracker_action

Why this command shape, and not the other ones

VariationResult
am startservice -a il.co.syntax.location_tracker_actionFails — the app is in idle (no live activity), so Android 8+ background-service rules forbid starting a regular service.
am start-foreground-service -n <cls>Works — explicit component, foreground variant. Same outcome as below, but doesn't exercise the implicit-intent matching.
am start-foreground-service -a il.co.syntax.location_tracker_action ✓Works because the service's manifest filter declares the action. The OS resolves the action to the LocationUpdatesService class, then bypasses the background-start ban thanks to the foreground promise.

Captured live on the A51:

$ adb shell am start-foreground-service -a il.co.syntax.location_tracker_action
Starting service: Intent { act=il.co.syntax.location_tracker_action }

The service shows its persistent notification within ~5 s (the foreground promise) and starts pulling location updates. From the user's perspective the app is "alive" forever, despite never having opened the activity.

Reflection answers

Q1 — Why is ACCESS_BACKGROUND_LOCATION in a separate Settings flow? Google's data shows that runtime prompts get dismissed reflexively. Burying background-location consent inside the Settings screen forces a user to actively navigate there, read what they're agreeing to, and toggle a switch. The friction is the point: it blocks the "while-in-use → always" silent escalation that was a real abuse pattern from circa 2016 family-tracker and ad-fingerprinting apps.

Q2 — Should pm grant be audited? Yes — and on production phones it effectively is, because pm grant requires the android.permission.GRANT_RUNTIME_PERMISSIONS system permission, which only signature-or-system apps and the shell UID hold. From a defender's standpoint, the audit point isn't "what did pm grant do" but "who got shell". USB debugging is the boundary; once it's enabled and authorised, a pm grant log is just one symptom among many. Production-grade EMM/MDM products do log all pm grant attempts on managed devices.

Q3 — Common pattern with the deep-link drill? Both apps perform a privileged action on behalf of an unauthenticated trigger. The defensive pattern that hardens both: require an explicit user gesture inside the app's own UI before performing the privileged op. For the SMS app, that means a confirmation screen even after a deep link arrives. For the location app, that means the service should refuse to start updates unless the activity has been resumed at least once in the last N minutes — the foreground service notification alone isn't enough. The general principle: external callers (intents, deep links, broadcasts) should be treated as suspect; the app's own UI is the one trusted gate.
