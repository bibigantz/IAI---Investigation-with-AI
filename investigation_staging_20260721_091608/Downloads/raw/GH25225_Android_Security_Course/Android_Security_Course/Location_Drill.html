Location Drill — Track a phone with permissions you don't tap to grant

Drive a location-tracking app entirely through ADB — install, read its manifest, grant runtime permissions silently, start the activity, start the service, and (the interesting part) restart the same service from idle state using its declared intent action and the start-foreground-service command. Slides 45–49 of Android Application.pptx.

What you'll learn

  • How to extract the package and component names from any APK using aapt2 dump xmltree — without unzipping the file by hand.
  • How pm grant bypasses the runtime permission dialog by writing directly to the package manager — only available because shell holds the right system-level permissions.
  • The difference between startservice (works only when the app has a foreground component) and start-foreground-service (works from idle, but the service must promote itself within ~5 s).
  • Why the foreground-service-with-notification model is what makes "background" location tracking actually possible on Android 8+.

1. Background — what does the location app do?

The il.co.syntax.location app is a deliberately simple location reader: tap "Start" on the main activity, it requests ACCESS_FINE_LOCATION, then a service connects to Google Play Services' Fused Location provider and prints street-level addresses to the screen. To stay alive while the user navigates away, it runs as a foreground service with a persistent notification — that's the contract the OS demands for any service that wants to be alive when no activity is visible.

The drill turns the same flow on its head: instead of tapping anything, you'll drive every step from adb, including granting the permission and starting the service from total idle.

2. Reading an APK's manifest with aapt2

aapt2 ships with the Android SDK build-tools. Two of its dump subcommands are particularly useful here:

aapt2 dump packagename app-location.apk
aapt2 dump xmltree   app-location.apk --file AndroidManifest.xml

The first prints the package name in a single line. The second decodes the binary AndroidManifest.xml from inside the APK and prints it as a readable tree, including every activity name, every service name, every intent-filter, and every requested permission.

You'll use this output to find: the package, the main activity class, the location service class, the runtime permissions the app needs, and (for the second part of the drill) the custom action string the service is registered for.

Setup before you start. The lab APK is in the course folder root as app-location.apk. Install it once, with -g if you want to skip the runtime-permission steps and move straight to the second part: 
adb install -r app-location.apk
# OR, to grant every permission upfront and skip the permission-grant exercise:
adb install -r -g app-location.apk

Exercise — Drive the location app entirely from ADB (slides 45–48)

Goal: never touch the phone. Make the app function as intended — start the main activity, grant location and notifications permissions, start the service, watch the address appear, force-stop. Then do it again, this time starting the service from idle with the right action.

  1. Install the app (without -g for now — you'll grant permissions in step 4).
  2. Read the manifest. Find the package name, the main activity class, the location service class, and the custom action string the service is registered to receive (you'll need it later).
  3. Start the main activity by name.
  4. Grant the runtime location permission. On Android 13+ also grant POST_NOTIFICATIONS so the service's notification can actually appear.
  5. Start the location service explicitly (-n). Confirm the address shows on the activity.
  6. Force-stop the app.
  7. Revoke the permission and try again. Revoke ACCESS_FINE_LOCATION from this same install, then start the activity, then start the service. Both commands return the same "started" message you've seen before — but does the service actually do anything? Open logcat while you trigger the service and read what's thrown. The instructive question: which layer enforces the permission, the activity manager or Fused Location itself?
  8. Once you're done observing, uninstall the app to reset state for the twist.
  9. Twist: reinstall, grant the permissions again, then force-stop the app so it's idle. Now start the service without opening the activity, using the service's manifest-declared action instead of an explicit component. Why does this need start-foreground-service and not startservice?
Hint 1 — Reading the manifest output

aapt2 dump xmltree prints lines like:

E: activity (line=14)
  A: android:name(0x01010003)="il.co.syntax.location.MainActivity"

Every activity, service, and receiver entry has an android:name attribute — that's the class. intent-filter entries have nested action entries with their own names — that's the action string you'll use in step 7. The location service has two filter actions; pick the one that does what you want.

Hint 2 — Granting runtime permissions silently

The pm grant command writes directly to the package manager's grant table — no UI involved. Use the full permission string (the one in the manifest uses-permission entries):

adb shell pm grant <package> <android.permission.XXX>

You can only pm grant permissions the app declared in its manifest, so check the manifest first.

Hint 3 — What does "without permission" actually fail at?

Both am start -n … and am startservice -n … succeed at the activity-manager layer — you'll see the same "Starting…" lines you've seen before. The components launch. The interesting question is what happens next:

  • On the activity — it opens, but instead of the address it shows an error message in its UI. The slide deck describes the app's design: "once the app receives the runtime location permission it can start the location service" (slide 44). In other words, the app's own code calls checkSelfPermission(ACCESS_FINE_LOCATION) on every "Start tracking" attempt and surfaces a permission-missing message to the user when it fails. The app itself is the first gatekeeper.
  • On the service — its onStartCommand runs, but the moment it asks FusedLocationProviderClient.requestLocationUpdates(...), Google Play Services checks the calling UID's permission and throws SecurityException: Caller … doesn't hold ACCESS_FINE_LOCATION in logcat. Even if the app forgot its own gate, the SDK would still refuse.

The lesson: permissions are enforced in two places — the app's own UI check, and the privileged API the app tries to call. Both are doing the right thing here. The activity manager itself does not gate per-component access on runtime permissions; it just launches what you tell it to. That's why am start "succeeded" — the OS isn't refusing the launch, the app and the SDK are refusing the operation.

To see both signals at once: adb logcat -v time | grep -iE "location|securityexception" in one terminal, then re-trigger the service in another.

Hint 4 — Why startservice from idle won't work

Android 8 (API 26) introduced background execution limits. From the slide: "An app with no running activities can't launch a regular Service but must use a Foreground Service that comes with a Notification." Translation: startservice from idle throws IllegalStateException; start-foreground-service works because it forces the service to display a notification within 5 seconds, which counts as "user-visible".

Hint 5 — Starting a service by action instead of component

Same syntax as activities, but use the service's intent-filter action:

adb shell am start-foreground-service -a <the-custom-action>

Don't pass -n — that's for explicit component, and you'd be back to the easy case. The point is to discover that the service can be addressed implicitly because it declared a public action in its manifest.

Hint 6 — Confirming location updates are happening

The app prints the resolved address on screen — but in idle state there's no UI. Either re-open the activity (am start) and check the activity's display, or use logcat:

adb logcat -v time | grep -i location

3. Why "background location" is actually foreground location with a notification

Slide 49 reminds you of a subtle point: even though the app keeps running when you press Home, in Android terminology this is still foreground — because the foreground service notification is visible. True background location (geofencing in deep idle, family-tracker in screen-off, missile alerts) requires a different runtime permission, ACCESS_BACKGROUND_LOCATION, which the user must grant in a separate Settings flow on Android 10+.

Why two permissions? Because background access is genuinely more sensitive — there's no notification, no UI, the app is invisible to the user yet still pulling GPS. Google split the permission so a tracking app can't quietly upgrade itself from "while the app is in use" to "always" — the user has to consent to each tier explicitly.

  2. You used pm grant to silently grant a runtime permission. From a defender's perspective: should the package manager log every pm grant call to a place the user can audit? What would that change?
