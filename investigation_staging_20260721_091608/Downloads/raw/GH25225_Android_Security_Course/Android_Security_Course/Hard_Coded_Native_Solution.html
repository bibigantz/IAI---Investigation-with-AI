Detailed walkthrough — Encryption #1 (slide 23)

How to find it: open hard_coded_app.apk in JADX-GUI, navigate to com.example.hardcodednativeapp.MainActivity, scroll to the companion object at the top of the class. The constant is named ENCRYPTED_STRING_1.

How to decrypt: open CyberChef. Paste CCZuCSI3I2kdIS43Iz09 into Input. Drag "From Base64" into the Recipe panel; then drag "XOR" below it. In the XOR step, set Key = FINDME, Key format = UTF8. Output reads No More Secrets.

Why this order — and what happens if you reverse it

The encoder did Base64(XOR(plaintext, key)). The decoder must therefore unwrap from outside in: Base64-decode first to recover the XOR'd bytes, then XOR with the same key to recover the plaintext.

If you reverse the steps in CyberChef and "XOR with FINDME" first, the XOR operates on the Base64 characters, not the underlying bytes. You'd get garbage that's not even valid Base64 anymore. CyberChef won't refuse — it'll just hand you nonsense.

Detailed walkthrough — Encryptions #2 and #3 (slides 24, 25)

How to find them: extract the native library from the APK first.

apktool d hard_coded_app.apk -o unpackapk

Or simply unzip the APK with any tool — APKs are ZIP files — and pull out lib/arm64-v8a/libhardcodednativeapp.so.

Open Ghidra: File → New Project → Import File → pick the .so → "Yes, analyze". Once analysis finishes, Window → Defined Strings.

Scroll the strings list:

  • Strings that look like mangled English (every letter shifted) — Encryption #2.
  • Long even-length hexadecimal strings — Encryption #3.

Decrypt #2 in CyberChef: paste Gur gehgu vf bhg gurer, recipe = ROT13, output = The truth is out there.

Decrypt #3 in CyberChef: paste 4150496b65793a533363726574504073737730726421, recipe = From Hex, output = APIkey:S3cretP@ssw0rd!.

Detailed walkthrough — Encryption #4 (slide 26)

How to find it: in Ghidra, look for the function (often named with a Java_ prefix) that returns a string but doesn't directly reference a string constant. Inside its body you'll see:

  • A 256-byte array being initialised in a loop (the RC4 S-box, slide 20 hint).
  • A nearby string constant hacktheplanet — the RC4 key.
  • A second array of bytes: 0xb7, 0x04, 0xe6, 0x8b, ... (slide 17 reminder: native code stores these in reverse on little-endian platforms; mentally reverse if the disassembly shows them as one 32-bit constant 0x8be604b7).

Decrypt in CyberChef: paste the byte sequence without the 0x prefixes (CyberChef's "From Hex" handles either, but pure hex is more reliable). Recipe = From Hex → RC4 (key = hacktheplanet, key format = UTF8). Output = No Where To Hide.

RC4 telltale signs in disassembly

SignatureWhat it looks like
S-box initfor (i = 0; i < 256; i++) S[i] = i; — a tight loop with index 0..255 writing into a 256-byte buffer.
Key schedulej = (j + S[i] + key[i % keylen]) & 0xff; followed by a swap. The and 0xff is the modulo-256 wrap that the slide flags as the giveaway.
Byte stream loopA second loop that XORs each ciphertext byte with S[(S[i]+S[j]) & 0xff]. Same and 0xff pattern.

Reflection answers

Q1 — Rank the four hiding methods, weakest to strongest:

  1. Hex (Encryption #3) — long hex strings stand out in any strings dump and decode with one CyberChef step. Trivially detectable, trivially reversible. The weakest.
  2. ROT13 (Encryption #2) — also visible to any strings dump, but at least requires recognising the encoding. Trivially reversible once recognised, and "looks like ROT13" is a recognisable pattern any analyst learns in the first hour.
  3. Base64 + XOR (Encryption #1) — slightly stronger because the XOR step requires recovering a key. But the key is in the same source file, retrievable by anyone who can decompile Kotlin. Effective only against an attacker who runs strings and stops there.
  4. Hex byte array + RC4 in native code (Encryption #4) — the strongest of the four because the key and the algorithm both live in machine code that requires Ghidra (or comparable) to read. An automated strings-only scan won't find a usable plaintext at all. But it's still defeated by a competent reverse engineer in under an hour.

Q2 — Native libraries: two reasons they're better, one reason they're not:

  • Better #1: not decompiled by JADX. JADX handles DEX/Java only; .so files are opaque to it. An attacker has to add Ghidra (or IDA/Hopper/Binary Ninja) to their toolchain.
  • Better #2: compiled native code carries no symbol names for local variables or parameters; ProGuard's name obfuscation is irrelevant because there's nothing to name. The structural information (control flow, function calls) survives but is harder to follow than Java.
  • Not as good as it sounds: a determined attacker uses Ghidra for free, the analysis is the same flavour they'd do on any iOS app or Windows binary, and the secret itself is still in the binary. Native-code obfuscation buys time, not safety. And critically: any string constant — even in a .so — appears in a flat strings dump unless you split it across multiple constants and recombine at runtime.

Q3 — How to ship an API key without hiding it in the binary:

  1. Don't ship the API key. Ship instead an authenticated session your own server creates, scoped per-user.
  2. Your server holds the third-party API key. Your app talks only to your server; your server forwards (with the third-party key) to the third party.
  3. Authenticate the user-to-your-server connection however your app already does (Firebase auth, OAuth, etc.).
  4. Rate-limit aggressively per user account so even if a user reverse-engineers their own session token, they can't burn your third-party quota.

Cost: an extra hop per API call, an extra service to maintain. Benefit: the third-party key never leaves your infrastructure. There is no way to extract it from an APK that doesn't contain it. This is the only architectural pattern that actually defeats the "an attacker has the binary" attacker model — every other approach is friction, not protection.
