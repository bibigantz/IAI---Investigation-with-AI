Hard-Coded Native App — Find every secret in the APK

An app hides four secrets across two layers — two in Kotlin constants (MainActivity.kt), two in the native library (.so). Each one uses a different encoding or encryption shape. Your job is to identify the shape of each one from clues in the data, then decrypt it with CyberChef. The reference table in §2 lists the shapes you might see; it's on you to recognise which is which. Use JADX for the Kotlin layer, Ghidra for the .so layer. What you'll learn

  • Why hard-coded secrets in mobile apps are a fool's errand — the binary ships to the attacker's hands.
  • How to triage a Kotlin/Java code base in JADX: search by string, by symbol, by constant.
  • How to recognise four common encoding/encryption shapes by sight: Base64, ROT13, hex, and stream-cipher byte arrays.
  • How to read native code in Ghidra well enough to spot hardcoded keys and recognise an RC4-style key schedule.
  • How CyberChef chains operations into recipes that decrypt all four examples without writing a line of code.

1. Background — why "hard-coded" is irreversible (slide 16)

Once a secret ships inside an APK, the secret has been sent to every user. The user owns the APK file; nothing prevents them from copying it elsewhere, decompiling it, and extracting whatever you put inside. Encryption doesn't help by itself, because the decryption key has to ship too — and if it ships, an attacker can find it.

This means hard-coded secrets are obfuscation at best, never security. The right model: assume an attacker with a copy of your APK and a few hours can extract any constant you put in it. Mitigations like ProGuard/R8 (Day 4 slides 27–30) raise the cost of finding it, but never make it impossible.

This drill walks you through finding each of four secrets the lab APK hides, in increasing order of difficulty.

2. The four encoding/encryption shapes you'll see (slide 17)

ShapeHow to recognise it by eyeReverse it with
Base64 (encoding, not encryption)String of letters, digits, +, /, ending in = or ==. Length divisible by 4. Every 3 input bytes become 4 output characters from the 64-char alphabet (A–Z, a–z, 0–9, +, /). Example: QVBJS0VZOm15c2VjcmV0MTIz decodes to APIKEY:mysecret123.CyberChef "From Base64"
XORComments or variable names mentioning XOR; key string visible nearby. Usually combined with Base64 because raw XOR output isn't ASCII. The key is repeated cyclically — if the key is 6 bytes and the plaintext is 60, byte 7 is XOR'd with key[0] again.CyberChef "XOR" with the key (set Key Type to UTF8)
ROT13String that looks like English but every letter is shifted by 13 (A→N, B→O, …). Non-letters unchanged. Example: Gur gehgu vf bhg gurer → The truth is out there. Self-inverse — running ROT13 twice returns the original.CyberChef "ROT13"
HexLong string of 0-9a-f, even length. Each byte → two hex characters. Example: ABC → 414243. In native disassembly, byte arrays are stored in reverse byte order on little-endian platforms — the array 0xb7,0x04,0xe6,0x8b appears as the constant 0x8be604b7 in Ghidra. Read carefully.CyberChef "From Hex"
RC4 (stream cipher)Byte arrays 0xab, 0xcd, …; modulo-256 ops (AND 0xFF in assembly); a key string nearby. RC4 generates a pseudo-random keystream from the secret key and XORs it byte-by-byte with the plaintext. Used historically in TLS and WEP — now deprecated in TLS by RFC 7465. If you see modular-256 indexing in a function that XORs each byte, it's almost certainly RC4 or close cousin.CyberChef "RC4" with the key

Combinations. Base64 and hex are encodings, not encryption — alone they only stop casual reading. Real apps usually combine them with XOR or RC4: encrypt first, then encode the binary output to ASCII so it can sit safely in a Kotlin string. Decoder applies the operations in reverse order: From Base64 → XOR (or RC4 → From Hex if hex was the outer wrapper).

3. Why developers hide secrets in .so files (slide 19)

Two of the four secrets in this APK are in the Kotlin layer; two are in the native library at lib/<abi>/libhardcodednativeapp.so. The native library is where developers think they're winning, because:

  • The DEX layer is just a single archive that any standard tool (JADX, ApkTool, Bytecode Viewer) reverses to readable Java/Kotlin in seconds. Constants jump out of the source.
  • A .so is platform-specific machine code — ARM64, ARMv7, x86, x86_64. There's no "decompile to Kotlin" step. Tools have to lift it back to pseudo-C, and the result looks nothing like the original. That gap raises the work the attacker has to do.

That said, "raises the work" is the entire defence — it doesn't break. Strings are still strings inside the binary. The Ghidra Defined Strings window dumps every constant the binary contains. Hardcoded keys, hardcoded URLs, hardcoded API tokens — all visible without lifting a single instruction. The native layer is a speed bump for opportunistic attackers, not a wall for motivated ones.

Workflow: JADX first (fast, surfaces three things at once: the Kotlin constants, the JNI external fun declarations, and the System.loadLibrary("native-lib") call). Then Ghidra on the .so for the remaining secrets, navigating from the JNI export names you collected.

Exercise — Decrypt all four secrets

The APK hides exactly four secrets. Your job: find each one, identify the shape it's wrapped in (encoding, cipher, or combination), and decrypt it. You'll know you got it right when the plaintext is human-readable. The reference table in §2 names the shapes you might encounter — it's on you to recognise which is which by the visual fingerprint of the data and (for the native ones) the routine surrounding it.

  1. Secret #1: a Kotlin constant in MainActivity.kt — look inside a companion object block. The string's alphabet is restricted, comes in fixed-length blocks, and has recognisable padding. Once you decode that outer shape, the bytes are still garbled — there's a second transformation layered on top, and the key for it is in the same file.
  2. Secret #2: a string constant inside the native library. Looks like English at a glance, but every word is gibberish — same letters, different positions.
  3. Secret #3: another native string constant. Long, even-length, alphabet limited to 0-9a-f.
  4. Secret #4: a byte array constant in the native library plus the routine that decrypts it. To finish this one you have to read the routine in Ghidra and recognise the cipher it implements — the key is a separate string in the data segment nearby. What to scan the routine for: a fixed-size working buffer that's filled in before any input is touched, then used to transform the input one byte at a time. The buffer's size is the giveaway — only one classic stream cipher family uses a buffer of that exact size. Once you can name the cipher, CyberChef has it as a single operation.

Hint 2 — Full CyberChef recipe for Secret #1 (open only if stuck)

Slide 23 gives the recipe and the captured input verbatim:

Input:    CCZuCSI3I2kdIS43Iz09
Recipe:   From Base64 → XOR with key "FINDME" (UTF-8)
Output:   No More Secrets

The order matters: From Base64 first, then XOR. Reversed, you'd be XOR'ing the still-encoded characters and getting garbage. Why this order? Because the encoder XOR'd plaintext first, then Base64-encoded the XOR output to make it ASCII-safe. Decoder undoes them in reverse.

Hint 3 — Extracting native strings with Ghidra (for Secrets #2 and #3)

The native library is at lib/arm64-v8a/libhardcodednativeapp.so inside the APK (also x86_64, armeabi-v7a, x86). Two ways to extract it:

  • Easy: right-click the APK → "Open with archive manager" (or use any unzip tool — APKs are ZIP files). Pull out the lib/arm64-v8a/libhardcodednativeapp.so.
  • Tool: use apktool d hard_coded_app.apk -o unpackapk (slide 18 notes). The .sos end up in unpackapk/lib/.

Then in Ghidra: File → New Project → Import the .so → "Yes" to analyze. Open Window → "Defined Strings" (slide 20) for a list of every string constant in the binary. Scroll for a string that looks like ROT13 (mangled English) or for a long hex string.

Hint 6 — Recognising the cipher in Ghidra: structural fingerprints (no spoiler)

The decryption routine for Secret #4 has three structural fingerprints. Each is suggestive on its own; all three together point at one specific classic stream cipher:

  • A 256-byte working buffer initialised in a tight loop before any input byte is touched. Often filled with values 0–255, then permuted using the key. This is the cipher's "state array" / S-box.
  • Indices wrapped at byte boundaries: look for and 0xFF / and 0xff, <reg> in the assembly, or i = (i + 1) & 0xFF in the pseudo-C. The cipher uses two indices, both wrapped mod 256.
  • The key is a short ASCII string in the data segment, read byte-by-byte during the state-array setup. Find it by scrolling Ghidra's Defined Strings window for a short word that looks like a password (lowercase, mnemonic, ~10–15 chars).

Once you have all three signals, search the web for "256-byte S-box stream cipher" or "stream cipher with 256-entry state" — the algorithm name is the top result. With the name, CyberChef has it as a single operation. The next hint gives the full recipe and key.

One last gotcha when copying the byte array out: native code stores byte arrays in reverse byte order on little-endian platforms (slide 17). The array 0xb7, 0x04, 0xe6, 0x8b appears in Ghidra as the 32-bit constant 0x8be604b7. Mentally reverse the bytes when copying them out for CyberChef.

Hint 7 — Full CyberChef recipe for Secret #4, with exact knob settings (open only if completely stuck) 
Input:    0xb7,0x04,0xe6,0x8b,0x11,0xa8,0xdc,0x28,0x7f,0xc0,0xd4,0x79,0x4b,0x10,0xa8,0x27

Recipe — two operations chained:

  1. From Hex — Delimiter: Auto
  2. RC4 — Passphrase: hacktheplanet with encoding UTF8; Input format: Latin1; Output format: Latin1
Output:   No Where to Hide

The format knobs matter. CyberChef's RC4 defaults to UTF8 for input/output format, which corrupts non-ASCII bytes during the intermediate XOR step and gives garbage. Switching both Input format and Output format to Latin1 treats every byte as a raw byte 0–255 and lets the cipher work correctly. (The passphrase encoding stays UTF8 because the key is plain ASCII.) Slide 26 prints the output as "No Where To Hide" with a capital T — the actual CyberChef output is lowercase "to". The slide has a typo.

Hint 8 — Pinning the JNI exports in Ghidra (slide 20)

For each native function the Kotlin code calls via external fun, the .so exports a symbol prefixed with Java_. Use Symbol Tree → Functions → search for Java_ to list them all. Each one corresponds to one Kotlin external fun declaration; finding which Java function calls each one in JADX gives you the call-graph anchor between the two layers.
