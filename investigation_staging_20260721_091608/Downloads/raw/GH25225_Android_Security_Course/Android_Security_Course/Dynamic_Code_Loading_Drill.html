Dynamic Code Loading Drill — Loading code that wasn't in the APK

An app can fetch a .dex or .jar file from the network at runtime, load it through DexClassLoader, and execute methods inside it — all with the host app's permissions. This drill shows the build pipeline (jar → dex with d8), the loading code, and why this pattern is so attractive to malware. Slides 12–15 of Android Vulnerabilities.pptx.

Before you start — what's provided vs. what you build.

The host app is already written and shipped with the lab in two forms. You do not need to write or modify the host code shown in Section 3 — that section exists so you understand what the host app is doing when it loads your dex.

  • Recommended — pre-built APK (dynamic_code_loader.apk). Install it once. At every launch pass your dex's SHA-256 as a launch extra: adb shell am start -n com.example.dynamiccodeloader/.MainActivity --es hash <your-64-char-hex>. No Android Studio, no Gradle, no source edits. See Plan B at the top of the Exercise.
  • Alternative — Android Studio source project (DynamicCodeLoader/). Open it, paste your dex's SHA-256 into the expectedDexHash constant in MainActivity.kt, hit Run ▶.

Your work is the attacker side, top-to-bottom: write Calculation.kt in IntelliJ → build the JAR → d8 to classes.dex → hash it → serve it with py -m http.server 8000 → adb reverse the tunnel → launch the host with your hash → see your code run inside the host's process.

What you'll learn

  • What "dynamic code loading" means at the JVM/DVM level — and why it's not the same as just running a downloaded executable.
  • How to take a normal Java/Kotlin module, package it as a JAR, and convert it to Android's DEX bytecode with the d8 tool.
  • Why downloaded code inherits the host app's permissions — no second prompt, no second review.
  • What integrity controls Android offers (SHA-256 hash check, Android 14's writable-dex restriction) and what they do not protect against.

1. Background — what is dynamic code loading?

An ordinary Android app ships its code inside the APK as a single classes.dex (plus optional split DEX files for large apps). At install time, ART verifies and stores those DEX files; at runtime, the OS loads them into the app's process. Nothing else gets executed.

Dynamic code loading breaks that model. The host app — at runtime, after install — fetches an extra .dex file from somewhere (a server, an asset, another file on the device), passes it to DexClassLoader, and uses Java reflection to invoke methods inside it. As far as the OS is concerned, those methods are running inside the host app's process, with the host app's UID, with the host app's permissions, and with no additional consent from the user.

From slide 13: "the malicious code doesn't have to ask for permissions explicitly because it inherited the permissions of the host app." That sentence is the entire security story.

2. The build pipeline — jar → dex (slide 14)

The pipeline has four steps: write the class in a normal IntelliJ project, export it as a .jar through IntelliJ's Artifacts mechanism, run Android's d8 tool to convert that .jar to a .dex, hash the result, and upload it to a server.

Step 0 — The Calculation example class

Slide 14 uses this minimal Kotlin class as the payload. It does nothing malicious — the payload's contents are not the point; the loading mechanism is. In a real attack the same class would do whatever the attacker pleased, with the host app's permissions:

package com.example.dynamic

class Calculation {
    fun div(a: Int, b: Int): Int {
        return a / b
    }
}

Create a fresh IntelliJ Kotlin (JVM) project, drop this single file into src/main/kotlin/com/example/dynamic/, and let IntelliJ build it. Don't use an Android Studio project — you want a plain JVM module so the output is portable Java bytecode that d8 can convert. The package, class, and method names must match what the host app reflects on (com.example.dynamic.Calculation.div(Int,Int)) — change any of them and the load fails with NoSuchMethodException or ClassNotFoundException.

Step 1 — Compile to a .jar (IntelliJ Artifacts)

IntelliJ's "Artifacts" feature is how you tell the IDE to package compiled classes into a deployable file. The menu path is identical on Windows, macOS, and Linux:

  1. Open File > Project Structure (Windows: Ctrl+Alt+Shift+S · macOS: ⌘ ;).
  2. In the left pane select Artifacts.
  3. Click the + icon, then JAR > From modules with dependencies…
  4. In the dialog: pick your module from the dropdown, leave Main Class empty (this is a library JAR — the host app calls into it, it has no main), choose an output directory for the JAR (default is out/artifacts/<module>_jar/).
  5. Click OK, then Apply, then OK again to close Project Structure.
  6. Build the JAR: Build > Build Artifacts… > <your JAR> > Build. After it finishes, the output directory contains a .jar file — typically untitled.jar if you didn't rename the artifact, otherwise <artifact-name>.jar.

Verify the JAR contains the expected class:

jar tf untitled.jar
# Expected output includes:
#   META-INF/MANIFEST.MF
#   com/example/dynamic/Calculation.class
Common mistake: if you click JAR > Empty instead of From modules with dependencies, you get a JAR with a manifest but no class files. The build will succeed and the resulting JAR will be useless. Always pick From modules with dependencies for the lab.
Troubleshooting — "Abnormal build process termination" on Build. If the build dies with a long Java command line and an error (on macOS Apple Silicon: rosetta error: Attachment of code signature supplement failed; on Windows: a similar build-process-terminated message with no clear cause), the project SDK is too old. IntelliJ sometimes picks up an older JDK (8/11/15) that current OSes don't run cleanly.

Fix: File > Project Structure > Project > change SDK to 17 or newer > OK > rebuild. That's it. No need to touch the Modules tab.

You don't need to download anything — IntelliJ ships its own JBR (matching your machine's architecture) at <IntelliJ install>/jbr. Add it via Project Structure > SDKs > + if it isn't already in the dropdown. Otherwise Temurin 21 from adoptium.net is a clean install (pick Windows x64 or macOS aarch64).

Step 2 — Convert the .jar to .dex with d8

The Android SDK ships d8 as part of its build-tools. Locate the binary, then run it against your JAR with --output . to drop the resulting classes.dex in the current directory.

OSPath to d8
Windows (cmd / PowerShell)%LOCALAPPDATA%\Android\Sdk\build-tools\<ver>\d8.bat
macOS~/Library/Android/sdk/build-tools/<ver>/d8
Linux~/Android/Sdk/build-tools/<ver>/d8

The command shape from slide 14:

<path-to-android-sdk>/build-tools/<version>/d8 --output . your-jar-file.jar

Worked example from the slide (macOS):

/Users/erankatsav/Library/Android/sdk/build-tools/36.1.0/d8 --output . untitled.jar

Worked example for Windows:

%LOCALAPPDATA%\Android\Sdk\build-tools\36.1.0\d8.bat --output . untitled.jar

The output is a classes.dex in the current directory. (For modern Android Gradle Plugin 8+ projects, d8 is invoked through Gradle as part of the build — calling it directly here is just for the demo, per the slide note.)

Step 3 (optional) — SHA-256 hash for integrity

Take a hash of the dex you just produced. The host app embeds this string and verifies the downloaded bytes match before loading.

OSHash command
Windows (cmd)certutil -hashfile classes.dex SHA256
Windows (PowerShell)Get-FileHash classes.dex -Algorithm SHA256
macOS / Linuxshasum -a 256 classes.dex

Embed that hex string in the host app as a constant. On download, recompute the hash of the bytes you received and refuse to load if it doesn't match — this is the slide's recommended hardening.

Step 4 — Serve the dex from your PC

The host app fetches the dex over the network at runtime. For the lab, the simplest "server" is Python's built-in HTTP server running on your PC. The complete runtime flow has three moving parts that all need to be set up correctly — they're covered in section 4 below.

3. The loading code in the app — reference only, already written in the host (slide 15)

This is the code that lives inside the provided host app. You are not writing it. Read it once so you understand what the host does when it receives your dex, then move on to Section 4 to wire up the lab.

Inside the host app, the runtime flow is four bullets:

  1. Download the .dex file from an external source.
  2. Calculate and verify the SHA-256 hash to ensure file integrity.
  3. Load the file with DexClassLoader.
  4. Invoke a method in the dynamically-loaded class and display the result.

The download + verify wrapper

val dexFileUrl  = "https://syntax.org.il/xtra/classes.dex"   // replace with your URL
val dexFilePath = downloadDexFile(dexFileUrl, filename = "classes.dex", context = this@MainActivity)

// Verify file integrity
val isVerified = verifyDexFileIntegrity(dexFilePath, expectedDexHash)
if (isVerified) {
    // Load and execute the dex file only if verified
    withContext(Dispatchers.Main) {
        loadAndExecuteDex(dexFilePath)
    }
} else {
    Log.e("DynamicLoading", "Dex file integrity check failed")
}

Line-by-line:

  • dexFileUrl — the server URL where the dex was uploaded in step 4 of section 2. Hardcoded as https://syntax.org.il/xtra/classes.dex in the lab; for your own test runs, replace with http://<your-laptop-ip>:8000/classes.dex.
  • downloadDexFile(...) — a helper that opens an HTTP connection, streams the body to a file in the app's private storage, and returns the path. The context argument is needed so the helper can resolve context.filesDir as the destination.
  • verifyDexFileIntegrity(...) — opens the downloaded file, runs MessageDigest.getInstance("SHA-256") over its bytes, and compares the result to expectedDexHash (the constant you embedded at build time). Returns true only on exact match.
  • withContext(Dispatchers.Main) { loadAndExecuteDex(...) } — the loading + reflection happens on the main thread. The download/verify above runs on a background coroutine; the withContext switch is only for the UI-touching part.
  • The else branch — failed integrity check is the most important branch in the whole snippet. If it logs and bails out, an attacker who replaced the dex on the server gets nothing. If a real implementation were to log a warning and load anyway, the entire SHA-256 check is theatre.

The reflection block (inside loadAndExecuteDex)

// Load the Calculation class dynamically
val calculationClass    = dexClassLoader.loadClass("com.example.dynamic.Calculation")
val calculationInstance = calculationClass.newInstance()

// Use reflection to call the `div` method
val divMethod = calculationClass.getMethod("div", Int::class.java, Int::class.java)
val result    = divMethod.invoke(calculationInstance, 90, 3) as Int

This is the moment the downloaded code starts running:

  • dexClassLoader.loadClass("com.example.dynamic.Calculation") — resolves the class by its fully-qualified name, exactly as it appears in your IntelliJ project. The string must match the package declaration of Calculation.kt (com.example.dynamic) and the class name (Calculation). Returns a Class<?> handle.
  • calculationClass.newInstance() — calls the no-arg constructor on the freshly-loaded class and returns an instance. (Deprecated since JDK 9 in favour of getDeclaredConstructor().newInstance(), but still works on Android.)
  • calculationClass.getMethod("div", Int::class.java, Int::class.java) — looks up the method by name and parameter types. The Int::class.java syntax is Kotlin's way of getting the JVM java.lang.Integer.TYPE token. Returns a Method handle.
  • divMethod.invoke(calculationInstance, 90, 3) — calls instance.div(90, 3). The return type is Any?, so we cast to Int. Result here is 30.

That's the entire trick. The Calculation class did not exist in the host APK at install time. The OS had no chance to inspect it, ART had no chance to verify it as part of the install. The first time anyone other than the attacker sees it is the moment div(90, 3) returns 30 — and at that moment the code is already running with the host app's UID, holding all of the host app's permissions.

Slide 15 in the deck shows add(5, 3) → 8 as the example. The shipped lab APK reflects on div instead — same mechanism, different method. Whichever method you put in your dex, the host app's reflection string has to match it exactly.

Android 14: setReadOnly() on the dex file

From the slide: dexFile.setReadOnly() //Solution for Android 14

Android 14 (API 34) refuses to load a .dex from a path the calling app can write. The OS reasoning: a writable dex is a TOCTOU window — the file you hashed at t=0 can be different from the file ART maps at t=1. Refusing writable dex closes the window structurally.

The fix in the host app is to call file.setReadOnly() on the downloaded dex after the integrity check and before handing the path to DexClassLoader. The OS is then willing to load it because the file is no longer writable by the app's own UID. Without this call, the loadClass on Android 14+ throws a SecurityException and the demo silently fails.

4. Running the lab on your PC + USB-connected A51

The phone has no SIM and no Wi-Fi, so we tunnel the PC's HTTP server back over the USB cable with adb reverse. Three things have to be alive at once: (1) a Python HTTP server on the PC in the folder holding classes.dex, (2) the USB tunnel via adb reverse, (3) the host APK built with the right URL and cleartext allowed.

adb reverse in one paragraph

adb reverse tcp:8000 tcp:8000 tells the phone: "any connection you make to your own 127.0.0.1:8000, send it down the USB cable to my 127.0.0.1:8000 instead." From the app's point of view the dex server lives on the phone; really it's the Python server on your PC. The tunnel survives app launches but dies on unplug, reboot, or adb kill-server — re-run the command if any of those happen. adb reverse --list shows what's active.

Configure the host APK (one-time)

Open DynamicCodeLoader in Android Studio. In MainActivity.kt, confirm val dexFileUrl = "http://127.0.0.1:8000/classes.dex". If you built your own dex (instead of using the bundled one), paste its SHA-256 into expectedDexHash — certutil -hashfile classes.dex SHA256 on Windows, shasum -a 256 classes.dex on macOS/Linux.

Build & install with Android Studio's Run ▶ button (Shift+F10) once the A51 is selected as the target device. That handles compile, install, and launch in one click.

Setup recipe (run every session)

:: terminal 1 — leave open
cd C:\path\to\folder-with-classes.dex
py -m http.server 8000

:: terminal 2 — one-liner, then close
adb devices                          :: confirm phone is attached
adb reverse tcp:8000 tcp:8000
adb reverse --list                   :: expect "UsbFfs tcp:8000 tcp:8000"

:: in Android Studio: Run ▶  (Shift+F10)

The phone shows a Toast with the result; Android Studio's Logcat tab (filter by tag DynamicLoading) shows the success trace:

D/DynamicLoading: Calculated file hash: 22c0705e...
D/DynamicLoading: Result of dynamic method: 30

And the Python terminal mirrors the request:

Exercise — Build the payload, host it, hijack the host app

You are going to play the attacker for the full pipeline: write the dynamic class in IntelliJ, package it as a JAR, convert to DEX, hash it, host it locally, plug the hash into the host project, install, and watch the host app execute your code. Then change the class once more without rebuilding the host APK — that's the whole point of dynamic loading.

Plan B — if the Android Studio project won't open. Use the bundled dynamic_code_loader.apk instead. It's the same source pre-built with a small lab convenience: it reads the expected SHA-256 from a launch extra. You skip stages 4 and 5's Android Studio work entirely and pass your payload's hash on the command line at every launch. 
:: install the prebuilt APK once
adb install -r dynamic_code_loader.apk

:: every time you have a fresh classes.dex on the server:
adb shell am start -n com.example.dynamiccodeloader/.MainActivity --es hash <your-64-char-hex>

The relevant line in the host source is just an override on top of the embedded constant — read it once so you understand what's happening, then forget about it:

// in MainActivity.onCreate, before the coroutine launches
val effectiveHash = intent.getStringExtra("hash") ?: expectedDexHash
…
val isVerified = verifyDexFileIntegrity(dexFilePath, effectiveHash)

If the launch extra is supplied, it wins; otherwise the embedded constant is used. This is a lab shortcut, not a real-app pattern — production apps always embed the hash, never trust an external source for it. Do stages 1–3 and 6 normally; replace stages 4–5 (and bonus stage 7's "edit expectedDexHash") with the --es hash launch above.

Stage 1 — Write the Calculation class in IntelliJ

  1. Open IntelliJ. New Project → Kotlin (JVM, not Android). Pick JDK 17 or newer (see the troubleshooting box in section 2.1 if you hit "Abnormal build process termination").
  2. Create the file src/main/kotlin/com/example/dynamic/Calculation.kt. Use this skeleton: 
    package com.example.dynamic

class Calculation {
    fun div(a: Int, b: Int): Int {
        return /* your code here — see below */
    }
}
    The fully-qualified name must be com.example.dynamic.Calculation, the method must be div(Int, Int): Int, and the package and JAR layout must be exactly that — those are the strings the host app reflects on. Change any and the load fails with NoSuchMethodException or ClassNotFoundException.
  3. Make the body do something memorable that isn't a / b — the host always invokes div(90, 3), so the result you see on screen tells you whether your code ran. If you write return a / b you'll see 30 either way, which proves nothing. Pick something distinctive, e.g.: 
    return a + b           // returns 93 for div(90, 3)
return a * b + 777     // returns 1047
return 42              // returns 42 regardless of input — easiest to spot
    Write it down so you can confirm the on-phone Toast matches what you wrote. The fact that calling a method named div can return whatever you like is itself the security point — the method name is a label, not a contract.
  4. Build the JAR: File → Project Structure → Artifacts → + → JAR → From modules with dependencies, leave Main Class empty, OK, Apply, OK. Then Build → Build Artifacts → <your JAR> → Build. Output lands at out/artifacts/<artifact-name>_jar/<artifact-name>.jar (typically untitled.jar).

Stage 2 — Convert the JAR to DEX with d8

From a terminal in the directory holding the JAR:

:: Windows
%LOCALAPPDATA%\Android\Sdk\build-tools\36.1.0\d8.bat --output . untitled.jar

:: macOS / Linux
~/Library/Android/sdk/build-tools/36.1.0/d8 --output . untitled.jar

Result: classes.dex in the same directory.

Stage 3 — Hash the DEX

certutil -hashfile classes.dex SHA256        :: Windows
shasum -a 256 classes.dex                    :: macOS / Linux

Copy the 64-character hex string. You'll paste it into the host project in the next stage.

Stage 4 — Wire it into the host project

  1. Unzip the DynamicCodeLoader project (the version shipped with this lab — cleartext is already enabled in the manifest).
  2. Open the unzipped folder in Android Studio (File → Open… → pick the DynamicCodeLoader folder, not the inner app folder). Wait for Gradle sync to finish — the bottom status bar should say "Gradle sync finished" with no red badges. If the project fails to sync (red errors, missing SDK, broken Gradle, JDK mismatch you can't resolve), stop here and switch to the Plan B callout at the top of this exercise — it skips Android Studio entirely.
  3. Open app/src/main/java/com/example/dynamiccodeloader/MainActivity.kt. Replace the value of expectedDexHash with the hex string from stage 3.
  4. Confirm the URL line reads val dexFileUrl = "http://127.0.0.1:8000/classes.dex".
  5. Copy classes.dex from stage 2 into a folder of your choice — call it C:\dex-server\ for the rest of this exercise.

Stage 5 — Start the server + tunnel, then Run from Android Studio

Two terminals first (the server and the tunnel have to be alive before the app launches, otherwise the download fails):

:: terminal 1 — leave open
cd C:\dex-server
py -m http.server 8000

:: terminal 2 — one-liner, then close it
adb reverse tcp:8000 tcp:8000

Now in Android Studio, with the DynamicCodeLoader project open and your A51 selected as the target device in the toolbar, just hit the green Run ▶ button (Shift+F10). Android Studio compiles, installs, and launches the app for you — no gradlew or adb install needed. If the build or install fails here for any reason you can't quickly resolve (Gradle errors, signing issues, target SDK mismatch), switch to Plan B at the top of this exercise.

Watch the result in two places:

  • The phone — Toast: "Dynamic code loaded successfully! Result: <your number>". The number should match what your stage 1 body returns for div(90, 3) — e.g. 93 if you wrote a + b, 1047 if you wrote a * b + 777, 42 if you hardcoded it. If the number matches what you wrote, your dex ran. That's the success criterion.
  • Android Studio's Logcat tab (View → Tool Windows → Logcat) — filter by tag DynamicLoading to see the three log lines from section 4.

The Python terminal also mirrors the request: "GET /classes.dex HTTP/1.1" 200.

Stage 6 (bonus) — Change the payload, watch the hash defence catch you

Stages 6 and 7 are optional. Stages 1–5 are the mandatory build-and-load pipeline; the bonus stages explore what the SHA-256 check buys you and what its absence costs.

Go back to IntelliJ. Change the div method to something different — say return a * b + 1000. Rebuild the JAR (Build → Build Artifacts → Rebuild), re-run d8, copy the new classes.dex into C:\dex-server\ overwriting the old one. Don't touch expectedDexHash. Re-launch the app.

Expected result: Toast "Dex file integrity check failed", plus E/DynamicLoading: Dex file integrity check failed in Logcat. The new bytes' SHA-256 doesn't match the constant baked into the host APK, so verifyDexFileIntegrity returns false and loadAndExecuteDex never runs. This is the host app's defence working. The hash check binds the host APK to one specific dex; you can swap the bytes on the server, but the host won't run them.

Stage 7 (bonus) — Update the hash and ship the new payload properly

Now play the legitimate developer flow: you have a new payload, you want it to run, the SHA-256 check is still in place. Recompute the hash of the new classes.dex and paste it into the host:

certutil -hashfile classes.dex SHA256        :: Windows
shasum -a 256 classes.dex                    :: macOS / Linux

In MainActivity.kt, replace the expectedDexHash constant with the new hex string. Hit Run ▶ in Android Studio. New result, new behaviour, integrity check passes — because the host APK now embeds the hash of this payload.

Compare what you just did to stage 6's failure: the bytes on the server are identical in both stages. The only difference is whether the host APK was rebuilt with the matching hash. The hash check moves the cost of every payload update onto a host-APK rebuild and reinstall. That's the security trade-off it imposes — you can't ship new code silently.

Hint — what to write down at the end
  • Stage 6 showed: the SHA-256 check binds the host APK to one specific dex. Swap the bytes alone, the load fails.
  • Stage 7 showed: a legitimate payload update requires recomputing the hash, updating the host, and re-shipping the APK. The check works as designed — at the cost of forcing every release through the same channel as a normal app update.
  • An attacker who left the check out (replaced verifyDexFileIntegrity(...) with true, or never wrote it) gets the opposite trade-off: every new file on the server runs at the next launch, with no APK update needed.
  • The Calculation class never existed in the host APK at install time. ART had no chance to verify it; Play Protect had no chance to scan it.
  • Everything ran with the host app's UID and permissions. If the host had INTERNET + READ_CONTACTS + RECORD_AUDIO, every new dex you served inherited all three.
Hint — what would catch this at scale
  • HTTPS for the dex URL: stops casual MITM, doesn't stop a compromised origin server.
  • SHA-256 check against an embedded hash (stage 6): stops anyone who can swap the bytes but can't ship a new APK. Forces the attacker to compromise the host app's release channel before they can ship a new dex.
  • setReadOnly() + Android 14's writable-dex refusal: closes a TOCTOU window between hashing and loading.
  • Code signing of the dex inside the host app (slide 13's "best"): the host stores a public key, the dex carries a signature, the host verifies the signature against the embedded key. This is what Google Play does for the APK; it's what mature dynamic-loading apps do for their dex. Lets the developer push new payloads without re-shipping the APK and still bind execution to keys only the developer holds.
