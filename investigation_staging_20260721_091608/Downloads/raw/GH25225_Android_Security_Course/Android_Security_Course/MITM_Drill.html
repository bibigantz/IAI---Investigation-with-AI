MITM Drill — Intercepting HTTPS, Defeating It With Pinning

Student walkthrough for the Man-in-the-middle drill. By the end you will use Burp Suite Community as a transparent HTTPS proxy for an Android app, install Burp's CA onto a Samsung Galaxy A51, see an app's Authorization: Basic header captured in cleartext inside Burp, and add certificate pinning to the app and watch Burp's MITM cert get rejected by name.

The lab uses the NetworkTraffic Android Studio project and the network-traffic.apk build it produces. The backend is the public https://httpbin.org/basic-auth/user/passwd endpoint, so every request reaches a real server and you can see real 200 / 401 responses on the phone.

All instructions assume Windows 10 / 11 PCs (the dominant lab environment). Where commands differ on macOS / Linux the alternative is given in a side row of the same table.
Read this before you start: undo the proxy when you're done. This drill sets a system-wide HTTP proxy on the phone (adb shell settings put global http_proxy <ip>:8080). If you walk away with that still set and Burp isn't running, the phone will look like it has Wi-Fi but no internet — every request hits a dead listener. Always run §13 Teardown before unplugging, or at minimum adb shell settings put global http_proxy :0. If you forgot and the phone is no longer near the PC, fix it on the device: Settings → Connections → Wi-Fi → long-press your network → Manage network settings → Proxy → None.

Allow inbound traffic on port 8080 (Windows Firewall)

Burp's listener will bind to 0.0.0.0:8080, but Windows Firewall blocks inbound TCP 8080 from other devices on the LAN by default. The phone will look like it's "doing nothing" because every connection attempt is silently dropped at the firewall — no error in Burp, no error in adb, just nothing.

Two ways to allow it:

  1. The first time you launch Burp, Windows pops a "Allow Java(TM) Platform SE binary to communicate" dialog. Tick "Private networks" and click Allow access. Done.
  2. If you missed the dialog or want to be sure, run PowerShell as Administrator and: 
    New-NetFirewallRule -DisplayName "Burp Suite (LAN, lab only)" `
                    -Direction Inbound -Protocol TCP -LocalPort 8080 `
                    -Action Allow -Profile Private
    To remove the rule after the lab: 
    Remove-NetFirewallRule -DisplayName "Burp Suite (LAN, lab only)"
This is the #1 reason the drill silently fails on Windows. If your phone shows the trust-anchor error and Burp's HTTP history is completely empty (not even failed connections), your firewall is dropping the phone's packets — the request never reached Burp at all.

1. Mental model — why this drill works at all

When the phone trusts the PC as its proxy, every HTTPS request from the app first hits Burp, not the real server. For each request Burp:

  1. Accepts the phone's CONNECT httpbin.org:443 (or whatever target).
  2. Generates a new server certificate on the fly signed by Burp's own CA (CN=PortSwigger CA).
  3. Performs the TLS handshake with the phone using that fake cert.
  4. If the handshake succeeds, decrypts the request, shows it in Proxy → HTTP history, and forwards it to the real server.

Step 3 is where the security model lives. The phone will only accept the fake cert if the chain ends at a CA the phone trusts. Vanilla Android does not trust user-installed CAs for app traffic on API 24+ (i.e. apps with targetSdk 24+), and our app's targetSdk is 34. So we need two things to enable interception:

  1. The Burp CA must be installed in the phone's user trust store (Settings UI).
  2. The app must declare a Network Security Config that explicitly trusts user CAs.

The supplied app already does (2) — open app/src/main/res/xml/network_security_config.xml to see it. Step (1) is what you do during the lab.

The Phase 2 part of the drill (pinning) is what defeats this whole chain even when (1) and (2) are both in place: pinning checks specific public keys in the cert chain and refuses any chain that doesn't match — Burp's fake cert can be valid for the hostname yet still get rejected because its SPKI doesn't match the pin.

If you can't get the phone onto the same subnet (different SSIDs, AP isolation, etc.), there are two fallbacks:
  1. Switch Wi-Fi networks on the phone. Settings → Connections → Wi-Fi → forget the current SSID and join the one that's on the same college LAN as the PC. Re-run adb shell ip route to confirm the new src is in the PC's /24.
  2. Tunnel Burp through USB with adb reverse. Same trick the Dynamic Code Loading drill uses. Keep Burp's listener on 127.0.0.1:8080 (don't switch it to All interfaces), then on the PC: 
    adb reverse tcp:8080 tcp:8080
adb shell settings put global http_proxy 127.0.0.1:8080

If the phone and PC are already on the same network (the normal lab setup: phone on Wi-Fi, PC on Ethernet, both on the college LAN), you don't need either fallback — the §5 proxy command pointing at the PC's LAN IP just works.

Verify reachability before continuing

From the PC, ping the phone to confirm the two endpoints can route to each other across the lab network:

adb shell ip route

Look at the src value (e.g. src 10.0.0.17) — that's the phone's IP on the Wi-Fi side. Then on the PC:

ping <phone-IP>

If ping times out, the two endpoints aren't routable — likely on different segments (phone on guest Wi-Fi vs PC on staff LAN, or AP isolation between Wi-Fi clients and the wired side).

6. Phase 3 — see the trust-anchor error (the "before" state)

From the folder where network-traffic.apk lives (the course root):

adb install -r network-traffic.apk
adb shell am start -n com.example.networktraffic/.MainActivity

In the app, type user / passwd and tap Login.

Expected on the phone screen:

❌ Network / TLS error
SSLHandshakeException: java.security.cert.CertPathValidatorException:
Trust anchor for certification path not found.

This is the right answer at this stage. The app reached Burp, Burp tried to MITM with a freshly-minted cert signed by CN=PortSwigger CA, but the phone has never been told to trust PortSwigger CA, so the TLS handshake fails. Without the next step the lab would be over.

The Authorization header was not transmitted, because TLS never completed. Burp's HTTP history will show the failed connection but no request body.

7. Phase 4 — push and install Burp's CA

There are two ways to get Burp's CA off the PC. Either works because every Burp project on the same machine uses the same persisted CA.

7a. Quickest — export the live CA from Burp

In Burp: Proxy → Proxy settings → Import / export CA certificate → Certificate in DER format → Next → save it. Suggested location:

OSWhere to save
WindowsC:\Temp\burp.der (create C:\Temp if it doesn't exist)
macOS / Linux~/Downloads/burp.der

Then push it to the phone:

adb push C:\Temp\burp.der /sdcard/Download/burp.der

(macOS / Linux: adb push ~/Downloads/burp.der /sdcard/Download/burp.der)

7b. Alternative — fetch over the proxy

While the phone is proxying through Burp, Burp serves its CA at http://burp/cert. From the PC:

:: Windows (cmd or PowerShell — curl is built in on Windows 10+)
curl -s -x http://127.0.0.1:8080 http://burp/cert -o C:\Temp\burp.der
adb push C:\Temp\burp.der /sdcard/Download/burp.der
# macOS / Linux
curl -s -x http://127.0.0.1:8080 http://burp/cert -o /tmp/burp.der
adb push /tmp/burp.der /sdcard/Download/burp.der

7c. Easiest — fetch directly on the phone's browser

While the phone is already proxying through Burp, open the phone's browser (Chrome, Samsung Internet, or any) and go to:

http://burp/cert

Burp intercepts that request and serves the CA cert directly to the phone. The browser saves it to Downloads as cacert.der. Skip the adb push step entirely — go straight to the install instructions below and pick cacert.der from the file picker.

This is the no-tools path: no curl, no PC-side file, no push — the phone fetches its own CA. The only requirement is that the proxy is already pointed at Burp (§5).

Now install it (Samsung A51 / One UI 5)

8. Phase 5 — see the Authorization header in Burp

adb shell am force-stop com.example.networktraffic
adb shell am start -n com.example.networktraffic/.MainActivity

Type user / passwd exactly, tap Login. Expected on the phone:

✅ 200 OK
Login succeeded.
{ "authenticated": true, "user": "user" }

Why those exact strings? The backend URL is https://httpbin.org/basic-auth/user/passwd — httpbin's basic-auth endpoint accepts only the credentials baked into the path. Any other input (e.g. alice / secret) returns 401 Unauthorized from the server. The Burp capture lesson works either way — the Authorization header lands in HTTP history before httpbin sees it (see §8.3) — but for the 200 OK screen above you need user / passwd verbatim.

In Burp:

  1. Open Proxy → HTTP history.
  2. Find the row to httpbin.org with method GET and path /basic-auth/user/passwd.
  3. Click it. The lower pane shows the Request tab — scroll to the headers and find: 
    Authorization: Basic dXNlcjpwYXNzd2Q=
  4. Right-click the value → Send to Decoder (or open Decoder manually, paste it, and choose Decode as → Base64).
  5. Output: user:passwd.

This is the lesson: Basic auth is encoding, not encryption. Anything sent inside HTTPS is private from third parties on the wire, but if a third party can be the server (which is exactly what Burp is doing here), the contents are plaintext to them.

8.1 Decode the credential outside Burp (sanity check)

Burp's Decoder is the easiest path, but you should be able to do this with any tool — that's the point. Pick whichever fits your environment:

ToolCommand / step
Windows — PowerShell[Text.Encoding]::UTF8.GetString([Convert]::FromBase64String('dXNlcjpwYXNzd2Q='))

All four return user:passwd instantly. No key, no secret, no math. That's what "encoding" means.

8.2 Forge a credential and replay it (Repeater demo)

If Burp can read the credential, an on-path attacker can also forge one. Show the class:

  1. In Burp, right-click the captured request → Send to Repeater.
  2. Switch to the Repeater tab.
  3. Build a fake credential on the command line:
    • Windows (PowerShell): [Convert]::ToBase64String([Text.Encoding]::UTF8.GetBytes('attacker:pwned'))
    • Windows (Git Bash) / macOS / Linux: printf 'attacker:pwned' | base64
    • Output (all): YXR0YWNrZXI6cHduZWQ=
  4. In Repeater, change the header to Authorization: Basic YXR0YWNrZXI6cHduZWQ= and click Send.
  5. httpbin returns 401 (because the credential is wrong) — but the request reached the server with a forged identity. Against a real backend that accepted those creds, the attacker would now be logged in as attacker.

The takeaway: pinning isn't paranoia. Without it, Authorization headers are both readable and rewritable on any device the attacker can install a CA on.

8.3 "But the server returned 401 — does that mean the password is safe?"

A common student question after seeing a 401 in Phase 5 (e.g. typing alice / secret123): "the server rejected it, so the attacker didn't get anything, right?"

Wrong. Burp captures the request before the server ever sees it. The flow is:

Phone → (TLS to Burp's CA) → Burp logs the full request → Burp re-encrypts → httpbin → 401 response
                                       ↑
                              attacker reads creds here

So even when the credentials are invalid, the attacker still walks away with the username, the (encoded) password, and the request shape — perfect for credential stuffing against a different service or for spray attacks.

To prove the request really reached httpbin and came back:

  • The Response tab in Burp shows HTTP/1.1 200 OK with the JSON body.
  • A 401 from httpbin appears if you submit anything other than user / passwd — but the Authorization header is still in HTTP history regardless.

9. Phase 6 — compute the SPKI pin you'll need

Pinning needs the SHA-256 of the public key of the cert you're locking to (the SPKI hash, not the hash of the whole certificate — common mistake). Generate it directly from a live TLS handshake against httpbin:

Windows note: the pipeline uses openssl, which Windows doesn't ship by default. Easiest path:
  1. Install Git for Windows (git-scm.com/download/win)
  2. Right-click anywhere on the desktop → Git Bash Here (or open Git Bash from the Start menu)
  3. Run the pipeline below in that Git Bash window — it includes a working openssl and bash.
If you'd rather stick with cmd/PowerShell, prefix with the full path: "C:\Program Files\Git\usr\bin\openssl". 
# Run in Git Bash (Windows) or any mac/linux terminal
echo | openssl s_client -showcerts -servername httpbin.org -connect httpbin.org:443 2>/dev/null \
  | openssl x509 -inform PEM -pubkey -noout \
  | openssl pkey -pubin -outform DER \
  | openssl dgst -sha256 -binary \
  | openssl enc -base64

The pipeline above produces one pin — the leaf cert's SPKI hash, because openssl x509 reads only the first PEM block from the chain. To get the intermediate pin, run the same pipeline against the second cert in the same TLS chain:

# Same source, but skip to the 2nd PEM block (the intermediate)
echo | openssl s_client -showcerts -servername httpbin.org -connect httpbin.org:443 2>/dev/null \
  | awk '/BEGIN CERT/{n++} n==2' \
  | openssl x509 -pubkey -noout | openssl pkey -pubin -outform DER \
  | openssl dgst -sha256 -binary | openssl enc -base64

Verified output at the time of writing this drill:

5BWYNtPxvjsl+qhQLxo3jz3ZaK74xyHT/QdOhBB07i0=        # CN=httpbin.org (leaf — primary pin)
vxRon/El5KuI4vx5ey1DgmsYmRY0nDd5Cg4GfJ8S+bg=        # Amazon RSA 2048 M03 (intermediate — backup pin)
++MBgDH5WGvL9Bcn5Be30cRcL0f5O+NyoXuWtQdX1aI=        # Amazon Root CA 1 (root — wider backup)

Why two pins, not one — and why we skip the root

Cert chain layers rotate at very different rates:

LayerRotationWhat pinning it gives you
LeafMonths (90–365 days)Tightest binding — only this exact cert is trusted. Breaks the app on every cert renewal.
IntermediateYears (3–5)Survives leaf rotations as long as the issuer doesn't change. Acts as longevity insurance.
RootDecades (10–20+)Survives intermediate rotation too — but trusts every cert ever issued under that root, which for Amazon Root CA 1 means millions of unrelated AWS-hosted sites.

The drill pins leaf + intermediate: leaf is the primary, intermediate is the backup so the app keeps working after the next leaf renewal without an APK update. The root is shown for completeness but not used in the pinned APK — pinning it would dilute the protection so much that an attacker with any AWS-issued cert could pass.

Pitfall — -binary matters. Without -binary, openssl dgst -sha256 prints the line (stdin)= aabbcc… as plain text and the next pipeline stage Base64-encodes that whole text — producing a wrong pin. Two earlier versions of this drill suffered exactly this bug. If your computed pin doesn't match the values above, double-check that flag.

  Peer certificate chain:
    sha256/<YOUR-BURP-SPKI>=:
        CN=httpbin.org,OU=PortSwigger CA,O=PortSwigger,C=PortSwigger
    sha256/<YOUR-BURP-SPKI>=:
        CN=PortSwigger CA, …
  Pinned certificates for httpbin.org:
    sha256/5BWYNtPxvjsl+qhQLxo3jz3ZaK74xyHT/QdOhBB07i0=
    sha256/vxRon/El5KuI4vx5ey1DgmsYmRY0nDd5Cg4GfJ8S+bg=
Notice that both sha256/<…> rows in the Peer certificate chain print the same hash. Burp Community Edition reuses its CA's public key when minting on-the-fly intercept leaf certs, so the leaf and the CA share an SPKI hash — OkHttp prints the same value for both rows. The hash itself is unique to your Burp install (Burp generates a unique CA per project) and won't match anyone else's. The two Pinned certificates values at the bottom are the constants from MainActivity.kt and will be identical for every student.

Read the chain Burp is presenting (top half) vs the pinned set (bottom half). The leaf cert claims CN=httpbin.org but is signed by PortSwigger CA — that's Burp impersonating httpbin. Its SPKI hash matches neither the real leaf pin nor the real intermediate pin, so OkHttp throws.

This is the win condition of the drill. Pinning defeats Burp interception, even though the user has trusted Burp's CA on the phone and the NSC explicitly accepts user CAs. The OS-level trust chain is no longer the deciding factor — the app pins specific keys.

12. Phase 9 — confirm pinning didn't break the legitimate path

Clear the proxy and re-test:

adb shell settings put global http_proxy :0
adb shell settings get global http_proxy
:: Expected: :0

Re-launch the app, log in. Expected screen: 200 OK again. The pinned chain (real httpbin leaf + real Amazon intermediate) matches what the cert pinner expects, so the request flows normally. A real user on real Wi-Fi never notices that pinning is on — only an attacker does.

15. Self-check — what you should be able to explain

By the end of the drill, in your own words:

  1. Why does Burp need to install a CA on the phone, and why does the app need a Network Security Config that trusts user CAs?
  2. What exactly does Burp do during a TLS handshake to "be" httpbin.org?
  3. Why is Authorization: Basic not actually a security feature?
  4. What is the difference between the certificate hash and the SPKI hash, and why is the SPKI the value we pin?
  5. Why does pinning still block Burp even though the device trusts Burp's CA system-wide?
  6. Why do we keep an intermediate as a backup pin, and what happens if you only pin the leaf?

If any of those are fuzzy, redo the relevant phase before moving on.
