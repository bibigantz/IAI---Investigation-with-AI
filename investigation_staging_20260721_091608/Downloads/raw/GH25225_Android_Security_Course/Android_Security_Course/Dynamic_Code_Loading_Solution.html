Dynamic Code Loading — Solutions

All commands taken from slide 14 of Android Vulnerabilities.pptx.

Solution — build the dex and verify its hash

# Convert JAR to DEX (slide 14 syntax, verbatim)
<path-to-android-sdk>/build-tools/<version>/d8 --output . your-jar-file.jar

# Slide example:
/Users/erankatsav/Library/Android/sdk/build-tools/36.1.0/d8 --output . untitled.jar

# Compute SHA-256 of the resulting classes.dex
shasum -a 256 file_name.dex

Why d8 and not dx?

dx was the original DEX compiler shipped with the Android SDK. d8 replaced it in build-tools 28+ — faster, more correct, and the only one supported on modern AGP. If you find a tutorial that says "run dx --dex …", it's pre-2018 and may not work on a current SDK install.

What the host app's loading code looks like (slide 15)

The flow inside the host app, in pseudocode:

byte[] dexBytes = downloadFromHttps("https://example.com/payload.dex");

byte[] expected = decodeHex("a3b2c1...");           // hardcoded constant
byte[] actual   = MessageDigest.getInstance("SHA-256").digest(dexBytes);
if (!Arrays.equals(expected, actual)) {
    throw new SecurityException("dex tampered");
}

File dexFile = new File(context.getCodeCacheDir(), "payload.dex");
Files.write(dexFile.toPath(), dexBytes, StandardOpenOption.CREATE_NEW);
dexFile.setReadOnly();   // Android 14 requires this before load

DexClassLoader loader = new DexClassLoader(
    dexFile.getAbsolutePath(),
    context.getCodeCacheDir().getAbsolutePath(),
    null,
    getClass().getClassLoader()
);
Class<?> clazz = loader.loadClass("com.example.payload.Calculation");
Method m = clazz.getDeclaredMethod("compute", int.class, int.class);
Object result = m.invoke(clazz.getDeclaredConstructor().newInstance(), 4, 7);

Every line of that code is reachable through JADX search. The defensive lines — SHA-256 compare and setReadOnly() — are present in the lab APK; check whether they're actually wired correctly (the demo code uses them; a real attacker would skip them).

Reflection answers

Q1 — Smallest set of signals that's a useful indicator:

  • App declares INTERNET (essentially every app does — by itself useless)
  • App's code references DexClassLoader, InMemoryDexClassLoader, PathClassLoader with constructor args derived from network input, or System.load/System.loadLibrary with paths derived from network input
  • App writes the file it then loads to a path it controls (i.e. file/load isn't a single static asset bundled in the APK)

Three signals together: network capability + reflective code load + writable-source-of-loaded-code. None alone is meaningful; the combination is the malware archetype.

Q2 — Why "writable" rather than "downloaded"? The OS can detect "writable" with one stat call; "downloaded" requires tracking provenance through the entire byte stream, which is fragile (an attacker just renames the file). Writable-vs-readonly maps cleanly to "could this file be modified after the app's last verification step" — exactly the property the integrity check needs to bind to. If the file is writable, an attacker who can write to that path can modify the bytes after the SHA-256 check and before the actual load (TOCTOU). Marking the file read-only between check and load is what makes the check meaningful.

Q3 — Defensive bar for merging a DexClassLoader call:

  • Source URL is HTTPS, hardcoded, with a pinned certificate (not a runtime-fetched URL).
  • SHA-256 of the expected payload is a constant in code or signed by a trusted offline key — never fetched from the same server as the payload.
  • Hash compare runs before the file ever touches disk (use InMemoryDexClassLoader).
  • Loaded class set is allowlisted by name — refuse loadClass(arbitraryUserSuppliedString).
  • Telemetry: log every successful and failed load so anomalies are visible.
  • Unit tests for the failure paths — bad URL, bad hash, partial download, file becomes writable post-check.

If the change author can't show all six, the merge waits.
