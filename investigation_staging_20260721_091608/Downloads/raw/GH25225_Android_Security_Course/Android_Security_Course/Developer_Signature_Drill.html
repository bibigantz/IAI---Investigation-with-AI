Developer Signature Drill — Student Guide

In this drill you will list every app installed on your Android phone and group them by the developer who signed them. By the end you will be able to:

  • Read an APK's signing certificate yourself
  • Recognise apps signed with the default Android debug keystore (every Android Studio install on Earth shares it)
  • Recognise apps that share a single corporate certificate (e.g. Google Mobile Services, Samsung core apps)
  • Recognise apps that have rotated their signing key (v3 signing scheme)
  • Use a SHA‑256 fingerprint to confirm two APKs come from the same developer

We use a Galaxy A51 connected over USB.

2. Tools used by the scripts

The scripts are thin orchestrators around standard SDK tools.

ToolWhere it runsUsed for

adb shell pm path <pkg>computer → phoneFind the on-device path to the APK file
adb pull <remote> <local>computer ← phoneCopy the APK back to the workstation
apksigner verify --print-certs --min-sdk-version 28computerPrimary signature reader. Handles APK Signature Schemes v1/v2/v3/v4
keytool -printcert -jarfilecomputerFallback if apksigner is unavailable. Reads only v1 (JAR) signatures, so it cannot read most modern Play Store apps
awk / grep (mac/linux) or Select-String (Windows PS)computerExtract the SHA-256 line from the tool's text output
Why pull each APK to the PC instead of reading it on the phone? apksigner is a PC-side tool (it lives in …\Android\Sdk\build-tools\<ver>\apksigner.bat) and takes a local file path as its argument — it has no way to reach over adb and read /data/app/~~xxx==/com.example.foo-yyy==/base.apk directly. So the APK bytes have to live on the PC's filesystem before the tool can hash them. The scripts pull each base.apk into a unique temp folder (Windows: %TEMP%\apksig_<guid>\, mac/Linux: /tmp/apksig.XXXXXX), run apksigner on it, and delete the whole folder when done — so the dump doesn't pollute your course folder and doesn't get picked up by the next zip rebuild.

3. What is a developer signature, really?

Every APK you install on Android — whether from Play Store, sideloaded from a .apk file, or built by you in Android Studio — has been signed by its developer. Without a valid signature, Android refuses to install it.

How signing works (one paragraph)

  1. The developer creates a keypair: a private key (kept secret) and a public certificate (shareable).
  2. When the build system finishes producing the APK, it computes a hash over the APK contents and encrypts that hash with the private key — that's the signature.
  3. The certificate (containing the matching public key) is bundled inside the APK.
  4. When the phone installs the APK, it decrypts the signature with the public key from the cert and compares it to a freshly computed hash of the APK. If they match → the APK has not been tampered with and it was signed by whoever holds the private key.

Why this matters for security

  • Same developer guarantee: app updates must be signed with the same key as the original install. So an attacker who repackages WhatsApp cannot push it to your phone as an "update" — Android refuses it.
  • Trust grouping: two apps signed with the same key are considered "the same developer" by Android. They can declare a signature-level permission to talk only to each other, or a sharedUserId to share storage.
  • Identity audit: you can pick any APK off any phone and ask "who signed this?" without trusting the developer's claim — the math doesn't lie.

The four signing schemes — v1, v2, v3, v4

Android has revised its signing format four times. Most modern APKs are signed with two or three of these at the same time for backward compatibility. Each scheme exists to fix a security or operational shortcoming of the previous one.

SchemeSinceWhat it addsWhy it matters
v1 (JAR signing)Android 1.0Hashes each individual file inside the APK; signature lives in META-INF/. Inherited from Java JAR signing.Has known flaws — files outside META-INF/MANIFEST.MF are not signed, which lets attackers inject content (the Janus vulnerability, CVE‑2017‑13156, exploited exactly this in 2017).
v2 (APK Signature Scheme v2)Android 7.0Signs the entire APK file as a stream, not file-by-file. Signature is stored in a dedicated "APK Signing Block".Closes Janus-class injection holes — every byte of the APK is covered. Also faster to verify (one hash, not one per file).
v3Android 9.0Everything v2 does + supports key rotation: the new signing key is embedded in the APK and signed by the old one.Lets a developer rotate to a new private key (e.g. after a leak) without losing the trust chain. WhatsApp, Google Photos, and Google Videos in our drill all use this.
v4Android 11.0A sidecar .idsig file containing a Merkle hash tree of the APK, enabling streaming verification.Used by adb install --incremental for huge game APKs — the OS can verify each chunk as it downloads, without buffering the full APK first.

Why this matters for the drill: an app signed with only v2 / v3 (i.e. most Play Store apps today) is invisible to keytool, because keytool was written for v1 JAR signing only. That's why the previous version of this script returned nothing for modern apps. apksigner reads all four schemes and is therefore the right tool.

What's inside a certificate?

When you run apksigner verify --print-certs base.apk you get fields like this:

Signer #1 certificate DN: CN=Eran Katsav, OU=Puzzle Appliactions, L=Kfar Varburg, ST=Israel, C=IL
Signer #1 certificate SHA-256 digest: 493028204afeae020d359264c5ec97680b13cff8ac52d286ee5e2cb42255f4b2
Signer #1 certificate SHA-1 digest:   cf1ffb40b37ace31550bcbbffeddcbde5ac7b1a0
Signer #1 certificate MD5 digest:     41bdb08532b373e07561e91c66d32db0
FieldMeaning
DN — Distinguished NameHuman-readable identity claimed by the cert's owner. Anyone can put any text here, so don't trust DN alone.
CN (Common Name)Person/product name (e.g. Eran Katsav, Android Debug, Google Inc.)
OU (Organizational Unit)Department / unit
O (Organization)Company name
L (Locality) — ST (State) — C (Country code, ISO 3166)Geographic claim
SHA-256 digestThe thing this drill cares about. See §4.
SHA-1 digestSame idea, older hash, kept for backward compatibility. Considered weak today.
MD5 digestEven older hash, broken cryptographically. Don't rely on it.

Key lesson: the only hard identity in a cert is its public key, summarised by the SHA-256 fingerprint. The DN text fields are like the name on a t-shirt — easy to lie about. The fingerprint is like the t-shirt's DNA — uniquely tied to the underlying private key.

4. What is SHA-256 and why this drill checks it

SHA-256 is a cryptographic hash function: feed it any input, get back a 256-bit (32-byte / 64-hex-character) value. Three properties matter for us:

  1. Deterministic — same input always produces the same output.
  2. Avalanche — change one bit of input and ~half the output bits flip. So two even slightly different certificates produce wildly different fingerprints.
  3. Collision-resistant — it is computationally infeasible to find two different certificates with the same SHA-256. With ~2128 work needed, "infeasible" means "no realistic adversary can".

In our context we hash the whole certificate (encoded in DER form). Result: a 64-hex string that uniquely identifies the cert. Two APKs with the same SHA-256 fingerprint were therefore signed by the same private key — i.e. by the same developer.

Why we use the fingerprint and not the certificate itself:

  • A certificate is a few KB of binary data. Comparing them directly is awkward; printing them is unreadable.
  • A 64-hex fingerprint is short, copy-pasteable, and one wrong character means "different cert".
  • All the slides, Play Console, Firebase, and Google Sign-In APIs identify apps by their SHA-256 (or SHA-1) signing fingerprint.
Why is the same value sometimes shown as 49:30:28:20:... and other times as 493028204afeae...? It's the same 32 bytes — just two display conventions. apksigner prints it lowercase without colons; keytool prints it uppercase with colons. Our scripts accept both formats and normalise internally.

5.2 What each group from the quick demo teaches

Group A — A6:64:9A:F7:D0:1A:... (3 apps: dynamiccodeloader, networktraffic, adbtraining)
DN: CN=Android Debug, O=Android, C=US. This is the default Android debug keystore that Android Studio creates the first time you run a project. Every developer in the world who has not configured a release keystore signs with the same key locally. So when you see A6:64:9A:F7:... (and DN of "Android Debug"), the app was almost certainly built and side-loaded from someone's laptop, not published to Play Store.

Group B — 49:30:28:20:4A:FE:... (3 apps: bipit, translateit, vocaller)
DN: CN=Eran Katsav, OU=Puzzle Appliactions, L=Kfar Varburg, ST=Israel, C=IL. This is the instructor's real release certificate. All three are PzlApps (Puzzle Applications) production builds installed from Play Store. Lesson: a single certificate fingerprint ties multiple apps to one author across multiple Play listings.

Group C — 5A:AD:2B:EE:6D:B9:... (2 apps: Photos, Videos)
DN: CN=Android, O=Google Inc.. Google's mobile-services release certificate. Many Google apps share this single cert, which is why they can declare signature-level permissions amongst themselves.

WhatsApp's two fingerprints (rotation)
WhatsApp introduced APK Signature Scheme v3 key rotation in 2022. The script reports the newest fingerprint (FB:92:0D:38:..., valid for Android 13+). The older fingerprint (39:87:D0:43:..., used on Android 7–12) is still embedded in the APK and will appear if you run apksigner verify --print-certs directly. Lesson: a developer can rotate to a new private key without losing the trust chain, by signing the new cert with the old one.

Wait — how do we know there's a second cert? The script only showed one!

Good catch. The script's grouped output for WhatsApp is just one line:

[1 app] FB:92:0D:38:1B:EE:... → com.whatsapp

That output by itself proves nothing about rotation. The script intentionally reports only the newest fingerprint per package — see §7.4: it grabs the first Signer line in apksigner's output and ignores the rest. If it reported every cert separately, WhatsApp would land in two groups and look like "two different developers", which would be misleading.

To actually see the two certs side by side, you have to run apksigner directly on the WhatsApp APK, bypassing the script's filter:

# 1. find the APK on the phone
adb shell pm path com.whatsapp

# 2. pull base.apk to your laptop (path will be something like /data/app/~~xxx==/com.whatsapp-yyy==/base.apk)
adb pull <that-path> whatsapp.apk

# 3. ask apksigner to print every signer
$ANDROID_HOME/build-tools/<latest>/apksigner verify \
  --min-sdk-version 28 --print-certs whatsapp.apk

You'll get two Signer (minSdkVersion=…) lines, like this (real format — same shape we'd see in any v3-rotated app, e.g. Google Photos):

Signer (minSdkVersion=33, maxSdkVersion=2147483647) certificate SHA-256 digest: fb920d38...
Signer (minSdkVersion=24, maxSdkVersion=32)         certificate SHA-256 digest: 3987d043...
Source Stamp Signer certificate SHA-256 digest: 3257d599...

Two Signer (minSdkVersion=…) lines = two certs in the APK. The first applies to Android 13+ (minSdkVersion=33), the second applies to Android 7–12 (minSdkVersion=24, maxSdkVersion=32). Each Android version picks the line whose range covers it. That's v3 key rotation.

This is also exactly what self-check task #1 in §9 asks you to do — pull a single APK and run apksigner on it directly. WhatsApp is one of the most interesting candidates because of this rotation.

What each big group teaches

[268 apps] 34:DF:0E:7A:9F:1C:... — the Samsung platform cert.
This is the most powerful key on the device. It signs android itself (the framework), every com.android.* (Bluetooth, NFC, phone, settings, SystemUI), every com.samsung.*, every com.sec.* (Samsung Galaxy launcher, camera, gallery, dialer), Knox, Samsung Pay, Bixby, all of Honeyboard. Apps signed with this cert get signatureOrSystem-level permissions automatically and can join android.uid.system, sharing the system UID's storage and IPC. Two implications:

  • Samsung re-signs the AOSP framework on Galaxy builds. android (the framework!) is here, not in a Google group. Samsung builds AOSP with their own platform key. That's how every OEM differentiates.
  • If this private key ever leaks, every Galaxy A51 in the world is owned forever. The OS will accept any APK signed with it as a system app. This is why platform keys are the most aggressively guarded secrets in mobile.

[44 apps] B9:A4:2D:D5:FC:4E:... — the AOSP/Samsung overlay cert.
These are not real apps. They are Runtime Resource Overlays (RROs) — drawable/string/dimension overrides bundled as fake APKs. They let Samsung switch the navbar style (navbar.gestural, navbar.threebutton), display-cutout shape (corner/double/hole/tall/waterfall), or font (font.notoserifsource, font.samsungone) without modifying the apps that consume those resources. A separate cert because they're shipped by the device as theming, not as functional apps.

[8 apps] 7C:E8:3C:1B:71:F3:... — the Google Mobile Services release cert.
Possibly the single most valuable signing key on Earth. Look at what it covers: com.android.vending (the Play Store itself), Gmail, Maps, GMS, Google Search, the Google Services Framework, calendar sync, Google TTS. Whoever holds this private key can ship any code as a "GMS update" to ~3 billion phones. Apps in this group share permissions amongst themselves via signature-level perms (so Maps can talk to GMS without user prompts).

How does Play Store install other apps if it's not platform-signed? The Play Store has the INSTALL_PACKAGES permission, which is signatureOrSystem — and it doesn't share Samsung's platform cert. It gets the permission via a third mechanism: it lives in /system/priv-app/ and the OEM ships an explicit allowlist XML at /etc/permissions/privapp-permissions-google.xml that names com.android.vending and the exact set of privileged perms it's allowed to hold (since Android 8 this allowlist is mandatory; before then every priv-app got every perm it declared, which OEMs were abusing for bloatware). So three tiers exist, not two: platform-signed (shares the framework's cert, ~268 apps), privileged (lives in /system/priv-app/ + named in an allowlist, e.g. Play Store), and regular system app (in /system/app/, no special access).

[7 apps] F0:FD:6C:5B:41:0F:... — Google's "legacy/system" cert.
Different from GMS: Chrome, Google Docs, Setup Wizard, partner setup, configupdater. Lesson: "Google" is not one cert. The company segregates signing keys across product families so that a leak of one doesn't compromise everything. (If GMS leaks, Chrome is still safe; if Chrome leaks, the Play Store is still safe.)

[3 apps] B9:21:09:B5:90:95:... — pre-installed Facebook bloatware.
com.facebook.appmanager, com.facebook.services, com.facebook.system. These ship on Samsung devices even if the user never had a Facebook account. They cannot be uninstalled — only "Disabled" via Settings — and they continue to consume RAM, battery, and network on first boot. Privacy talking point: a signed cert lets Samsung and Facebook agree on these apps surviving every system update.

[3 apps] 5A:AD:2B:EE:6D:B9:... — Google "video/photo family" cert.
Photos, Videos, YouTube. (YouTube was invisible in the -u scan because Samsung pre-installs it as a system app — it only appears in the full scan.)

[3 apps] A6:64:9A:F7:D0:1A:... — the Android Studio default debug keystore.
Same as in the quick demo. Sideloaded test apps signed with the universal debug key.

[3 apps] 49:30:28:20:4A:FE:... — instructor's release cert.
Same as in the quick demo. Real-world example of a small-scale developer reusing one cert across multiple Play Store listings.

[1 app] FB:92:0D:38:1B:EE:... — WhatsApp post-rotation cert.
The newest of WhatsApp's two embedded certs. The legacy cert (39:87:D0:43:..., used on Android 7–12) is still inside the APK to satisfy older devices, but the script reports the newest one (used on Android 13+).

The big takeaways from the full scan

  • One vendor cert dominates the device. ~63% of the packages on this A51 (268/423) share one Samsung key. That key is the de-facto root of trust for everything Samsung-branded.
  • "Google" is not one developer. At least three distinct Google certs ship on this A51 (GMS, legacy/system, video-family) — and there are more on the full output that we didn't show.
  • Apps share certs to share permissions. Two apps signed with the same key can declare signature-level permissions or sharedUserId between themselves with zero user friction. That's why Samsung apps talk to each other freely, and why Gmail can read the Maps storage if it wants to.
  • A debug-signed app on a stranger's phone is suspicious. All ~420 packages should have a corporate cert. Only sideloaded test builds show the Android Debug cert. If you find one and didn't install it, something is wrong.

5.4 What to find on YOUR phone

After you run the script, answer these questions:

  1. How many apps are signed with the debug keystore (CN=Android Debug)? These are sideloaded test apps. If you see one you didn't recognise, it might be malware someone installed.
  2. Which Play Store apps share a fingerprint with another app you have? (Hint: many vendor apps — Samsung, Google, Microsoft — group together.)
  3. Pick any Google app and verify its signature using APKMirror: go to https://www.apkmirror.com, search for the app (e.g. "Google Photos"), pick any version, scroll to the "App Info" section. APKMirror publishes the SHA-256 fingerprint of every APK they host. Compare it with the fingerprint your script reported — they should match. (Note: Google itself does not publish a public list of its app signing certificates, so APKMirror — which independently extracts and displays the fingerprint of each uploaded APK — is the most reliable third-party source.)
  4. Run the script in filter mode with the instructor's signature (-t 49:30:28:20:4A:FE:AE:02:0D:35:92:64:C5:EC:97:68:0B:13:CF:F8:AC:52:D2:86:EE:5E:2C:B4:22:55:F4:B2). It should match bipit, translateit, vocaller. If it doesn't, your apksigner is too old (see §7).

6. How to run the scripts

6.1 macOS / Linux — find_apps_by_signature.sh

# 1. mark executable (only first time)
chmod +x find_apps_by_signature.sh

# 2. group every package on the phone by developer (full system + user, ~10 min on a busy phone)

# 3. RECOMMENDED — group only the user-installed apps (~30 sec)

6.2 Windows — GetPackages.ps1 (PowerShell)

PowerShell ships with every Windows 10 / 11 install — there is nothing to install. Open the Start menu, type PowerShell, hit Enter, then cd into the course folder before running the commands below.

PowerShell is installed on every Windows 10/11 box. By default it refuses to run any .ps1 files at all — that's a safety feature called the execution policy, set to Restricted out of the box, intended to stop a stranger's script from running just because you double-clicked it. We don't want to weaken this globally, so for each invocation we pass -ExecutionPolicy Bypass which lifts the restriction only for that single command (the system-wide setting is untouched). Other useful flags: -NoProfile skips your PowerShell profile (faster startup), -File says "run this script file then exit". So the full command means: "PowerShell, lift the script-execution restriction just this once, run GetPackages.ps1 with these arguments, and quit."

# 1. group user-installed apps (~30 sec)
powershell -ExecutionPolicy Bypass -File .\GetPackages.ps1 -UserOnly

# 2. group every package (~10 min)
powershell -ExecutionPolicy Bypass -File .\GetPackages.ps1

# 3. filter to one cert (colons optional, lowercase or upper, both work)
powershell -ExecutionPolicy Bypass -File .\GetPackages.ps1 -UserOnly `
    -TargetSignature 49:30:28:20:4A:FE:AE:02:0D:35:92:64:C5:EC:97:68:0B:13:CF:F8:AC:52:D2:86:EE:5E:2C:B4:22:55:F4:B2

# 4. multiple devices — pick one
powershell -ExecutionPolicy Bypass -File .\GetPackages.ps1 -UserOnly -Serial R58R404WTXY

# 5. help
powershell -ExecutionPolicy Bypass -File .\GetPackages.ps1 -?

If you'd rather not type -ExecutionPolicy Bypass each time, run once in an elevated PowerShell:

Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
Unblock-File .\GetPackages.ps1

…and from then on .\GetPackages.ps1 -UserOnly works directly.

7. Important parts of the scripts (read this if it doesn't work)

The .sh and .ps1 do the same five things. Below are the non-obvious bits — every line was put there to fix a real bug encountered on the lab phone.

7.1 We use apksigner, not keytool

The original course script used keytool -printcert -jarfile. keytool only reads APK Signature Scheme v1 (the old JAR signing format). Modern apps signed with v2 or v3 only — that's almost every Play Store app today — come back as Not a signed jar file and the script silently produces nothing. This is why the previous version of the drill returned zero matches even when the signatures were on the phone.

The fix: use apksigner from build-tools, which understands all four signing schemes (v1, v2, v3, v4). keytool remains as a fallback for environments that don't have build-tools installed — but you'll be warned that the results will be incomplete.

7.2 We pass --min-sdk-version 28

apksigner verify --min-sdk-version 28 --print-certs base.apk

Without --min-sdk-version, apksigner insists on verifying all signature schemes the APK could be checked against. Many modern APKs have stripped their v1 manifest (META-INF/MANIFEST.MF) entirely because they target Android 9+. apksigner then errors out with DOES NOT VERIFY — Missing META-INF/MANIFEST.MF and refuses to print any cert info. By passing --min-sdk-version 28 we say "we don't care about pre-Android 9 verification", which makes apksigner happy and lets it print the v2/v3 certificates.

7.3 We always pick the newest installed apksigner

LATEST_BT=$(ls -1 "$SDK_ROOT/build-tools" | sort -V | tail -n 1)
APKSIGNER_BIN="$SDK_ROOT/build-tools/$LATEST_BT/apksigner"

build-tools versions ≤ 30.0.3 do not support --min-sdk-version correctly and will still fail on v2-only APKs. The script forces the newest installed version regardless of PATH. If you only have 30.0.3 or older, install something newer via Android Studio's SDK Manager (build-tools 33+).

7.4 We match ^Signer .*certificate SHA-256 digest:, not ^Signer #1 ...

apksigner prints two formats depending on the APK:

Signer #1 certificate SHA-256 digest: <hex>                                  (single signer)
Signer (minSdkVersion=33, maxSdkVersion=2147483647) certificate SHA-256 digest: <hex>   (v3 rotation)

A regex anchored on Signer #1 misses every app that has rotated keys — WhatsApp, Photos, Videos. The broader pattern ^Signer .*certificate SHA-256 digest: (note the space after "Signer", which excludes "Source Stamp Signer") catches both formats and we take the first match (which is the newest cert in v3 rotation).

7.5 We deliberately ignore "Source Stamp Signer"

Apps shipped through Play Store have an extra cert called the Source Stamp — Google adds this so Play Protect can detect tampering. It's the same cert (3257d599a49d2c961a471ca9843f59d341a405884583fc087df4237b733bbd6d) on every Play app, so grouping by it would lump every Play app together regardless of developer. Our regex only matches lines that start with Signer (a literal space), which excludes lines starting with Source Stamp Signer.

7.6 We pull only base.apk, not split APKs

Modern apps are delivered as App Bundles — multiple .apk files (base.apk, split_config.en.apk, split_config.xxhdpi.apk, etc.) installed together. Every split shares the parent's signature, so we save 3-5× of pull time by checking only base.apk (the first path that pm path <pkg> returns).

7.7 The progress line uses \r

printf "\r[%3d/%3d] %-60s" "$i" "$TOTAL" "$PKG"

Without this, students stare at a blank terminal for several minutes wondering if the script froze. The \r (carriage return without newline) lets us update one line in place. Same effect achieved in PowerShell with Write-Progress.

7.8 One bad APK no longer kills the whole scan

The original bug. On a Galaxy A51 running Android 11, students saw the script halt in the middle of the scan with:

Method invocation failed because [System.Object[]] does not contain a method named 'Trim'.

Cause: pm path <pkg> for some packages (split-APK bundles, Samsung dictionary/IME/billing stubs) returns multiple package: lines, one per APK file. The old one-liner

$apkPath = (& adb shell pm path $pkg | Select-Object -First 1) -replace 'package:', ''
$apkPath = $apkPath.Trim()

occasionally produced an Object[] instead of a single string, and .Trim() doesn't exist on arrays. Because $ErrorActionPreference = "Stop", that one bad package crashed the entire run.

The fix. Two changes:

  1. Replace the brittle one-liner with a defensive three-step parse: force pm path output into an array, filter to lines starting with package:, take the first, coerce to string, then trim.
  2. Wrap the whole per-package body in a try { ... } catch { ... }. Any failure on one APK is logged into a $skipped list with the reason, and the scan continues to the next package. The final summary prints both the developer groups and the skipped list.

Why mostly on Android 11 A51 and not Android 13 A51: the buggy pm path output came from older Samsung One UI 3 (Android 11) preinstalls — the dictionary stub, the v-voice IME, and the billing app, all packaged with an older Samsung build pipeline. One UI 5 (Android 13) rebuilt those packages and reorganised some into APEX modules, so they return clean single-line paths. Same bug class, just statistically more visible on the older image.

7.9 We fall back to keytool when apksigner says "DOES NOT VERIFY"

The second bug. On the same Android 11 A51, three specific preinstalls reproducibly failed apksigner with:

com.diotek.sec.lookup.dictionary
com.samsung.android.svoiceime
com.sec.android.app.billing

ERROR: JAR signer CERT.RSA: JAR signature META-INF/CERT.SF indicates the APK is
signed using APK Signature Scheme v2 but no such signature was found.
Signature stripped?

What's actually wrong with these APKs. Each one is signed only with the legacy v1 (JAR) scheme. However, the v1 manifest (META-INF/CERT.SF) contains the line X-Android-APK-Signed: 2 — the v1 signer's way of saying "a v2 block should also be present alongside me". The matching v2 block is missing. apksigner treats this discrepancy as evidence of tampering (someone may have stripped v2 to downgrade) and refuses to print the certificate. The phone's PackageManager doesn't make this strict check at runtime, so the APK runs fine on the device but our offline tool rejects it.

The fix. When apksigner returns no signature for an APK and keytool is available, the script now falls back to keytool -printcert -jarfile on a per-package basis. keytool predates the v2/v3 schemes entirely — it reads only the v1 (JAR) certificate and doesn't care about the X-Android-APK-Signed: 2 claim — so it extracts the cert cleanly. Successfully recovered packages are listed in a "apksigner failed and keytool succeeded" section at the end of the run, so students can see exactly which packages took the fallback path.

Result on a Samsung A51 / Android 11 lab phone: Scanned 452 packages, skipped 60, keytool fallback used on 3. The three keytool-recovered packages share a single SHA-256 (BE:1C:52:3F:…:28:58, OU=translator, O=voiceservice) — meaning the Diotek dictionary and the Samsung voice IME are signed by the same vendor. That's exactly the developer-correlation lesson the drill is teaching.

Why "skipped 60"? Those are RRO (Runtime Resource Overlay) APKs in /product/overlay/ and /vendor/overlay/. pm path reports their paths, but adb pull can't read them even though the Unix permissions show -rw-r--r-- (world-readable). The reason is SELinux: these files are labelled u:object_r:vendor_overlay_file:s0, and the policy doesn't grant the shell domain read access to that type. Files in /system/priv-app/ (which the script can pull) are labelled system_file, which shell is allowed to read. Same chmod, different SELinux type, different outcome — only root would bypass it. This is a useful real-world point: Android's file security has two layers (Unix DAC and SELinux MAC), and the second is what stops non-root tooling from reading vendor overlays.

9. Self-check tasks

When you're done running the script, prove you understand it by doing these:

  1. Pull a single APK off the phone and run apksigner verify --print-certs on it directly. Confirm the SHA-256 you see matches what the script reported for that package.
  2. Build a debug APK from any Android Studio project, install it on the phone, re-run the script, and confirm it lands in the A6:64:9A:F7:D0:1A:E4:3F:... "Android Debug" group.
  3. Find an app on Play Store, install it on a friend's phone too, run the script on both phones, and confirm the SHA-256 fingerprint is identical. (Demonstrates: a fingerprint is tied to the developer, not the install.)
  4. Take any Google app's fingerprint from your phone and look up the official Google fingerprint list — confirm it matches.
  5. Bonus: write a one-line shell pipeline that prints just the package names that share your signing certificate, given that you know the SHA-256 of your debug keystore.
