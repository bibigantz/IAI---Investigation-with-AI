Deep Link Drill — Solutions

All commands and URLs are taken from slides 41–42 of Android Application.pptx.

Solution — both methods

Method A: HTML link tapped from the file browser

The bundled test.html at the course folder root contains an input field and a link generator. The runtime-generated link looks like:

smssender://send?data=<number>:<urlencoded-message>

Push the file once, then open from the phone:

adb push test.html /sdcard/Download/test.html
# on the phone: Files app → Download → test.html → fill in fields → tap link

Method B: ADB directly (no HTML)

adb shell am start -a android.intent.action.VIEW -d "smssender://send?data=0506944922:hello"

# with a space-and-ampersand-bearing message:
adb shell am start -a android.intent.action.VIEW -d "smssender://send?data=+972506944922:Hello%20%26%20Welcome"

What's inside the URL

PieceRole
smssenderCustom scheme. The DeepLinkApp manifest registers an intent-filter with <data android:scheme="smssender" /> on its launch activity. Any app can register any scheme.
sendHost portion. The intent filter matches android:host="send"; another path on the same scheme could route to a different feature.
?data=...Query string. The app's activity reads getIntent().getData().getQueryParameter("data") in code.
: (in the data value)An app-specific separator chosen by the developer. Everything before : is the destination number; everything after is the message body. Note this is part of the value — the URL parser doesn't interpret it.
%20 / %26URL-encoding for space and ampersand. Required because raw space breaks URI parsing and raw & would split the query string.

What you'll see on the lab A51

The deep link reaches the app's launch activity, the activity parses the data= query parameter, and calls SmsManager.sendTextMessage. The carrier accepts the message and the SMS goes out — that is the demonstration of the attack: a tap on a webpage link caused the phone to send a real SMS without a confirmation dialog. logcat shows the app's "deep link received" trace.

Verifying the deep link landed

adb logcat -v time | grep -i "deeplink\|smssender"

Reflection answers

Q1 — Why allow arbitrary schemes? Two reasons. First, the system has to be extensible by third parties without Google sitting in the middle of every URL handler approval — that would re-create the App Store gatekeeping pattern at the URL layer. Second, the early Android model treated apps as cooperative peers; a fragmented scheme namespace was acceptable because the assumption was that the user installed only apps they trust. Modern Android tightens this with App Links, where an HTTPS link to your-domain.com can be claimed by an app only after you prove ownership of the domain via a .well-known file — but custom schemes still have no ownership check.

Q2 — Does the SMS-permission prompt mitigate this? Partially. The prompt forces the user to consent once. But after that grant, every deep link the app receives can fire SMS without a second prompt. From the user's point of view, "I allowed this app to send SMS for the legitimate use case" becomes "this app sends SMS whenever a website tells it to". The mitigation only works if the user thinks ahead about which other surfaces (browsers, file managers) can dispatch deep links into the app — most users don't.

Q3 — How would you defend a legitimate enterprise SMS sender?

  • Don't accept the destination number from the URL at all. Instead, require an authenticated session (e.g. enterprise SSO) and look up the destination from a server-side address book keyed on the session. The URL becomes "send a templated SMS to recipient X" where X is an opaque ID.
  • Show a confirmation screen for every send — even one that looks scary will be tapped through, but rate-limiting + visible recipient prevent the silent-batch case.
  • Use App Links instead of a custom scheme so only your verified domain can dispatch into the app.
  • Require that the calling Intent's android.intent.extra.REFERRER matches a trusted source (browser, file manager) and reject if it's missing or unrecognised.
