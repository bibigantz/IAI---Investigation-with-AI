Solution to Exercise 1

adb shell am start -n il.co.syntax.adbtraining/.SecondActivity

adb shell am start -a android.media.action.STILL_IMAGE_CAMERA
adb shell am start -a android.media.action.VIDEO_CAPTURE

adb shell am start -a android.intent.action.SENDTO -d sms:658765 --es sms_body "Hello\ World!"

# or, without --es, after the SMS window opens:

Argument breakdown

CommandWhat's happening
am start -n il.co.syntax.adbtraining/.SecondActivityExplicit intent. il.co.syntax.adbtraining is the manifest package; .SecondActivity is the relative class name (resolves to il.co.syntax.adbtraining.SecondActivity).
android.media.action.STILL_IMAGE_CAMERASystem action that any installed camera app can declare it handles. The OS shows the chooser if more than one matches.
android.media.action.VIDEO_CAPTURESame family — but specifically asks the camera app to start in video mode.
android.intent.action.VIEW -d geo:32.0833,34.8167VIEW is the most generic display intent; the URI scheme decides what type of "view". geo: resolves to the map app.
android.intent.action.SENDTO -d sms:658765SENDTO means "open a composer for this destination, don't send yet". The sms: scheme tells Android the target is an SMS; 658765 after the colon is the destination number.
--es sms_body "Hello\ World!"String extra named sms_body — that's the documented extra key the SMS composer reads to pre-fill the message body.
adb shell input text "Hello\ World!"Sends literal keystrokes to whichever window has focus. Useful when the app you're driving doesn't expose a documented extra for the field you want to fill.

Solution to the Bonus mission — three worked examples

The drill asks you to pick two actions from the docs page and try them. Here are three worked examples so you can see how the documentation maps to the command. All three were captured on the lab Galaxy A51 and visibly produced the expected behaviour on the phone screen.

Example 1 — Google web search

adb shell am start -a android.intent.action.WEB_SEARCH --es query "android\ security"

Captured: Starting: Intent { act=android.intent.action.WEB_SEARCH (has extras) }

Phone shows: the default browser opens with Google searching for "android security".

How the docs entry mapped to the command

Required input: SearchManager.QUERY ("query")One string extra named query--es query "..."
(no Intent.getData() reference)No data URI neededNo -d in the command

Example 2 — Pre-fill the alarm clock with a new alarm

adb shell am start -a android.intent.action.SET_ALARM \
  --ei android.intent.extra.alarm.HOUR 7 \
  --ei android.intent.extra.alarm.MINUTES 30 \
  --es android.intent.extra.alarm.MESSAGE "wake\ up"

Captured: Starting: Intent { act=android.intent.action.SET_ALARM (has extras) }

Phone shows: the Clock app opens directly on the "Add alarm" screen, with hour pre-set to 7, minutes to 30, and the label field filled with "wake up". You can either tap Save to commit or cancel out.

How the docs entry mapped to the command

This one's documented on a different class — android.provider.AlarmClock — not on Intent. The reference for it lists:

public static final String ACTION_SET_ALARM
Constant Value: "android.intent.action.SET_ALARM"

Optional Extras (selected):
  EXTRA_HOUR     "android.intent.extra.alarm.HOUR"     int
  EXTRA_MINUTES  "android.intent.extra.alarm.MINUTES"  int
  EXTRA_MESSAGE  "android.intent.extra.alarm.MESSAGE"  String
  EXTRA_SKIP_UI  "android.intent.extra.alarm.SKIP_UI"  boolean
Docs entryTranslated to command
Constant Value android.intent.action.SET_ALARM-a android.intent.action.SET_ALARM
EXTRA_HOUR (int)--ei android.intent.extra.alarm.HOUR 7
EXTRA_MINUTES (int)--ei android.intent.extra.alarm.MINUTES 30
EXTRA_MESSAGE (String)--es android.intent.extra.alarm.MESSAGE "wake\ up"

The --ei flag is for integer extras (the docs say "int" — that's your hint). The full extra key is the constant value from the docs (e.g. android.intent.extra.alarm.HOUR), not the constant name (EXTRA_HOUR) — easy to confuse.

If you append --ez android.intent.extra.alarm.SKIP_UI true, the alarm is created silently with no UI shown. Try it.

Example 3 — Start a 60-second timer

adb shell am start -a android.intent.action.SET_TIMER \
  --ei android.intent.extra.alarm.LENGTH 60 \
  --es android.intent.extra.alarm.MESSAGE "tea"

Captured: Starting: Intent { act=android.intent.action.SET_TIMER (has extras) }

Phone shows: the Clock app's Timer tab opens with a new 60-second timer labelled "tea", waiting for you to start it. Add --ez android.intent.extra.alarm.SKIP_UI true and the timer starts immediately with no UI.

The repeated pattern

By the third example you've seen the structure once and copied it twice. Every "open this app pre-filled" intent on Android is the same shape:

  1. Find the action's constant value in the docs → goes after -a.
  2. Find the extras' constant values → become --es / --ei / --ez / --el keys depending on type.
  3. If a data URI is documented → goes after -d.
  4. If the docs say "Optional: SKIP_UI boolean" — useful for testing whether the action also has a non-interactive code path the OS doesn't normally surface.

adb shell dumpsys meminfo | grep syntax     # activity-only — smaller footprint

# other commands worth knowing:
adb shell ps | grep syntax
adb shell dumpsys meminfo il.co.syntax.adbtraining     # OR by PID
adb shell am force-stop il.co.syntax.adbtraining       # OR by PID

Why the foreground variant is required

Android 8 (API 26) introduced background execution limits: an app that has no visible activity can no longer call startService(...). The replacement, startForegroundService(...) (and the corresponding am start-foreground-service), is a contract: "Android, please launch this even though I'm in the background — I promise to call startForeground(...) within five seconds, which will show a notification and demote me from the 'background' bucket."

If the service forgets to call startForeground in time, the framework throws ForegroundServiceDidNotStartInTimeException and kills the process. Try it: re-run the same command but pass --ez notif false and watch logcat — the service refuses to show its notification, the timer expires, and the process is terminated.

What the meminfo lifecycle teaches

Numbers below are real captures from the lab Galaxy A51 (Android 13) — your readings will be within ±10–20% depending on what's been GC'd, paged in, or just-rendered. The relative sizes are what matters.

StateProcess / label in dumpsys meminfoPSSRSSWhat you'll see
After force-stop———Empty. grep adbtraining returns nothing — every process the app owned is gone.
Activity only (MainActivity, no service)(pid N / activities)≈55–67 MB≈140–150 MBOne row. The /activities suffix tells you the process is hosting a visible Activity.
Service only (FGS started, no activity)(pid N) — no suffix≈27 MB≈95 MBOne row, smaller than Activity-only. No /activities suffix because no Activity is loaded. Contains MediaPlayer + audio buffers + network stack + the FGS notification, but no inflated UI.
Activity + service (both running)(pid N / activities)≈62 MB≈153 MBStill one row — both components live in the same process by default. Footprint ≈ Activity-only + a few MB for the service. The PID matches the Activity-only PID; no second process spawned.
Activity dismissed (swipe-up), service kept(pid N) — suffix drops≈48 MB≈137 MBSame PID survives. The /activities suffix is gone because no Activity is loaded, but the process is alive courtesy of the FGS. ~12 MB drop as the UI hierarchy is released.

Three lessons that come out of these numbers:

  • UI is heavy. Activity-only (~145 MB cross-view) is bigger than service-only (~99 MB) — inflated layouts, theme drawables, the View / Compose hierarchy, and graphics buffers cost more than a MediaPlayer plus a network socket.
  • Default IPC is "same process". Adding the service to an already-running Activity doesn't fork — both components share the process, the PID, and the heap. You see one row in dumpsys meminfo, never two.
  • FGS keeps the process alive after the Activity is gone. Swipe up to dismiss the Activity (or remove its task) and the process survives — the foreground service is its lifeline. The label loses /activities but the PID stays the same. This is the lifecycle the Day-3 Hidden Recognition capstone exploits.

adb install -g abnormal_app.apk

The contrast row-by-row:

RowBaselineAfter 20 s of Heavy-CPUDelta
Native Heap (PSS)~10 MB~12 MB+2 MB — barely moves
Dalvik Heap (PSS)~3.5 MB~140 MB+137 MB — explodes
Java Heap (PSS)~11 MB~148 MB+137 MB — explodes
TOTAL PSS~64 MB~198 MB+134 MB

So where is the abnormality? Not in the Native Heap (which barely moves) but in the Dalvik / Java Heap. That's because the Heavy-CPU button is a Kotlin loop allocating Java/Kotlin objects in tight succession — they all land in ART's managed heap (Dalvik / Java rows are two views of the same data), not the C/C++ malloc heap (Native row). Native Heap would only swell if the work went through JNI to C++ code.

Common misreading. The "Native Heap" line on the detailed row shows Heap Size = 222 MB even at baseline. That's the JVM's address-space reservation ceiling, not actual memory residency. The number that matters for "is this app heavy" is the PSS column — and PSS for Native Heap stays at ~10 MB throughout. Always read the PSS column, never the Heap Size column, when asking "how much real RAM is this using?".

CPU side, same scenario:

$ adb shell top -n 1 -b | grep abnormalapp
27333 u0_a518     10 -10  6.5G  272M  74M S  660   4.8   6:28.67 com.example.abnormalapp

%CPU = 660% on the abnormal app — pegging six to seven cores worth of compute. The slide's threshold for "abnormal" was 20–30%; we're more than an order of magnitude above it. The normal app at the same screen sits in low single digits, and on its meminfo the Dalvik / Java Heap rows stay near baseline.

What the contrast teaches

Two apps with the same package-name pattern, the same UI, identical install footprint — yet wildly different live behaviour. Without seeing source code, an analyst with only adb access can:

  • Distinguish between them in seconds via dumpsys meminfo and top.
  • Build a detection rule (e.g. "alert if package PSS > 100 MB and CPU sustained > 30% in absence of user interaction").
  • Cross-reference battery and network telemetry (slides 30 covers dumpsys batterystats, dumpsys netstats) to confirm the suspect is also draining battery and beaconing.

The Day 3 capstone (Hidden Recognition App) and Day 4 vulnerability hunting build on this same primitive: the live resource fingerprint is the most honest description of what an app actually does.

The grant/revoke round-trip (also captured)

$ adb shell pm revoke il.co.syntax.adbtraining android.permission.POST_NOTIFICATIONS
$ adb shell dumpsys package il.co.syntax.adbtraining | grep POST_NOTIFICATIONS
        android.permission.POST_NOTIFICATIONS: granted=false, …

$ adb shell pm grant il.co.syntax.adbtraining android.permission.POST_NOTIFICATIONS
$ adb shell dumpsys package il.co.syntax.adbtraining | grep POST_NOTIFICATIONS
        android.permission.POST_NOTIFICATIONS: granted=true, …

The toggle is instantaneous; the framework's permission table is updated atomically. shell can grant/revoke any runtime permission for any installed app whose manifest declares it, by virtue of the android.permission.GRANT_RUNTIME_PERMISSIONS system permission baked into com.android.shell.

StepWhat it triggers on the phone

Reflection answers

Q1 — Why does an implicit intent need a data URI? The action says what kind of operation ("VIEW something", "SENDTO somewhere"); the URI says which thing. Without the URI, the intent resolver has no way to pick between, say, the browser (which handles VIEW http://) and the dialer (which handles VIEW tel:). The URI is the second key the resolver matches against intent filters.

Q2 — Why typed extras? The receiver's contract is "I expect a String at key X, an int at key Y". If extras were untyped strings, every receiver would have to parse and validate them, and bad input could trip number-parsing crashes inside otherwise-trusted code. Typed extras shift the validation work to the framework's parcel deserializer, which is fast and centrally maintained.

Q3 — Is the music-from-any-URL service a security issue? Yes, but the locus is the service's design, not am. Any app that exports a service (or accepts launches via start-foreground-service from shell) and treats an arbitrary URL as input must validate that URL — at minimum HTTPS, ideally an allowlist of hosts. am is just the messenger; if someone can talk to the service via binder (e.g. another app using the same intent), the same exposure exists. Lesson for app authors: assume any string that crosses the IPC boundary is hostile.
